# ADR-056: One Loader For Users' Types And Blocks

## 1. Decision Summary

SciStudio runs Python that its users write: custom data types in
`<project>/types/`, custom blocks in `<project>/blocks/`, and the same two
directories in the user library under `~/.scistudio/`. This ADR decides how
the backend loads that code, how the rest of the product finds it, and how it
is replaced when it changes.

Users write imports as they would in a Jupyter notebook: a file is imported by
its file name. `from scverse_omics import AnnData` finds
`types/scverse_omics.py`, and `from scverse_bridge import to_anndata` finds
`blocks/scverse_bridge.py`. The target users are scientists who write little
code, and the AI agents that write code for them produce this form unprompted.

Each process will have one **user-code loader**. It registers every user file
exactly once, under the file's bare module name. The type registry, the block
registry, format-capability lookup, block instantiation and the worker will all
obtain user code from it, so a type has one class object per process. One
lookup API serves every consumer, and one identity rule decides whether two
classes denote the same type.

A user file whose name would shadow a standard-library module or an installed
package is refused, with a message that asks the user to rename it.

The backend does not restart on a project switch. Opening or switching a
project, editing a drop-in file, switching a git branch and installing a
package all run one clear-and-reload pass owned by the loader.

This is a Proposed ADR. It records the owner's September 16, 2026 decisions
made during the live test session of
[issue #2480](https://github.com/jiazhenz026/SciStudio/issues/2480). None of
the behavior it decides is implemented yet; implementation is tracked by
[issue #2483](https://github.com/jiazhenz026/SciStudio/issues/2483).

### 1.1 Problems Addressed

| Problem | Risk | ADR response | Detailed section |
|---|---|---|---|
| The same user file is loaded more than once in a process, under different module names | Strict type checks fail between two copies of one type ("SaveAnnData expected AnnData, got AnnData", #2480; #2134; #1950) | One loader registers each file once under its bare module name | Section 3 |
| A block file cannot import a sibling file in `blocks/` | The whole file is skipped and every block in it disappears (#2480) | Block directories become import roots beside type directories | Section 4 |
| Name collisions between user files and installed modules are handled for type files only | A block helper can shadow a library, or be shadowed, without any report | One collision rule for every user directory | Section 4 |
| Each consumer resolves user code and compares types its own way | New code paths reintroduce duplicate-class failures | One lookup API and one identity rule | Section 5 |
| Cleanup is spread over several mechanisms and is partial | Stale modules survive re-scans and project switches (#2017); a package-shaped type keeps stale submodules after an edit (#2480) | One clear-and-reload pass owned by the loader | Section 6 |
| The worker loads blocks by a different path from the backend | A block registers in the backend and fails or behaves differently when it runs | The worker builds the same loader from the same roots | Section 7 |
| Refused and failing user files are not reported where users look | Blocks vanish while reload reports `removed: []` (#2480) | One failure record, returned by every listing and reload | Section 8 |

## 2. Existing Behavior And The Actual Delta

Today user files are loaded by path in these places, each with its own module
name, import roots and cleanup:

| Consumer | Where | Module name used today |
|---|---|---|
| Block scan | `src/scistudio/blocks/registry/_scan.py` | `_scistudio_dropin_<stem>_<mtime>` |
| Type scan | `src/scistudio/core/types/registry.py` | `_scistudio_type_dropin_<stem>_<mtime>_<hash>` |
| In-process block instantiation | `src/scistudio/blocks/registry/__init__.py` | The synthetic name recorded on the spec |
| Format-capability lookup | `src/scistudio/blocks/registry/_capability.py` | A synthetic name |
| Worker | `src/scistudio/engine/runners/worker.py`, roots from `src/scistudio/engine/runners/process_handle.py` | The synthetic name, reloaded by path |
| Legacy project previewers | `src/scistudio/previewers/project.py`, `src/scistudio/previewers/session.py` | Synthetic names |
| Panel process | `src/scistudio/panels/bootstrap.py` | `panel` |
| Plot render harness | `src/scistudio/plot/_harness.py` | `scistudio_plot_render` |

**How types reach blocks today.** While blocks are scanned and run, the type
directories are prepended to `sys.path` (`dropin_import_roots_for_block_dirs`
in `src/scistudio/core/dropins.py`). This lets a block write
`from spectrum import SpectrumData` (ADR-053 personal tool library spec,
FR-012). That import creates a second module, `spectrum`, for a file the type
registry already loaded under a synthetic name, so the process holds two
`SpectrumData` classes.

Gates that compare classes have been taught a name-based fallback one at a
time:
- `same_registered_type` in `src/scistudio/core/types/base.py`, used by the save path;
- the port check since #2134.

`SimpleSaver.save` in `src/scistudio/blocks/io/simple_io.py` was not taught it,
which produced the #2480 failure.

**Block directories are not import roots today.** A block that imports a
sibling helper raises `ModuleNotFoundError`, and the whole file is skipped.

**Cleanup is spread today** over:
- bytecode eviction;
- `transient_dropin_modules`;
- bare-stem eviction inside the collision guard;
- `refresh_all_registries`;
- the standalone MCP bridge's `sync_dropins`;
- the panel service's own watcher (#2465).

**Interim fixes in #2480.** The reload responses gained the failure record,
`hot_reload` drops the blocks of a file that now fails, and the collision guard
evicts a package-shaped type's submodules. This ADR supersedes those mechanisms
with the loader's single pass.

**The delta this ADR decides:**
- one loader per process;
- bare module names in place of synthetic ones;
- block directories as import roots;
- one collision rule;
- one lookup API and identity rule;
- one clear-and-reload pass;
- worker parity.

## 3. One Loader And One Module Per File

Each process will own one user-code loader. Given the ordered user directories
for the active project (Section 4), it:

1. Finds every loadable `*.py` file. Names starting with `_` are skipped, as today.
2. Imports each file under its bare file name through Python's import system, so the module exists once in `sys.modules`.
3. Hands the modules to the type registry and the block registry. They register the classes each module defines. A class re-exported by another module is registered only from the module that defines it, as today.

The type registry and the block scanner will stop loading files themselves, and
the synthetic `_scistudio_*dropin_*` module names will be retired.

Because a user class's module name is then importable wherever the loader is
installed, `isinstance`, `issubclass` and pickle agree within one loader
generation.

## 4. Import Roots, Search Order, And Collisions

The loader installs one import finder for user code. The finder resolves bare
names against these roots, in precedence order:

1. project `types/`, then project `blocks/`;
2. user-library `types/`, then user-library `blocks/`.

The tutorial-scoped library replaces the user-library tier in a tutorial
project, as it does today. A project file shadows a user-library file of the
same name, which keeps the project-over-user precedence of ADR-053.

A block file can import a type file, a sibling helper, or another block file. A
block class imported into another file is registered only from its own file.

The finder answers only for names that exist in these roots and pass the
collision rule. A user file is refused when its bare name:

- is a standard-library module name;
- resolves to an installed top-level module or package; or
- appears more than once within one tier (for example `types/utils.py` and
  `blocks/utils.py` in the same project).

A refused file is not importable and registers nothing. Its refusal records the
file path and a message asking the user to rename the file. The installed
module keeps resolving to the installed package. This generalises ADR-053
FR-016 from type directories to every user directory.

## 5. One Lookup API And One Identity Rule

Every consumer will obtain user code by name, through the loader or the
registries built on it:
- a type name or type chain;
- a block type name;
- a user module name.

No consumer will load a user file by path.

One function will decide whether two classes denote the same data type, by
comparing registered type-name chains. Every type gate will call it:
- port compatibility;
- save and load dispatch;
- the `SimpleSaver` and `SimpleLoader` checks;
- format-capability matching;
- output validation.

Within one loader generation this agrees with `isinstance`, because each type
has one class object. The rule exists for objects created before a reload
(Section 6), which still carry the previous generation's classes.

## 6. Clear And Reload

The loader owns invalidation. One pass handles every trigger:
- project open and switch;
- drop-in create, edit and delete, including saves made through the app and changes seen by the standalone MCP bridge;
- git branch switch and working-tree restore;
- package install and uninstall;
- the Reload action and the `reload_blocks` tool.

The pass:
1. removes from `sys.modules` every module the loader created, identified by file location and including submodules;
2. resets the finder and calls `importlib.invalidate_caches()`;
3. evicts stale bytecode for changed files;
4. loads the current roots and rebuilds the type and block registries from the result.

The backend process is not restarted for any of these triggers (owner decision,
September 16, 2026). A restart on project switch was considered and rejected
(Section 11).

Each pass starts a new generation. Objects that already exist keep their
previous classes. Holders that live across passes, such as preview and panel
sessions, caches and in-flight runs, compare types with the identity rule of
Section 5 and resolve classes again through the lookup API when they need one.

## 7. Worker And Other Processes

A worker subprocess will receive the ordered roots for its project and build
the same loader before importing the block. It will import the block by its
bare module name and reconstruct inputs through the same registries. The type
checks inside a block then run against one class object per type.

The panel process (`src/scistudio/panels/bootstrap.py`) and the plot harness
(`src/scistudio/plot/_harness.py`) keep loading their own entry script. They
will install the same loader, so the entry script's imports of user types and
helpers follow Sections 3 to 5.

Project previewers under `previewers/` are deprecated and removed in 0.3.6.
Until then they keep their current loader and receive the user-code finder, so
their imports of user types resolve to the loader's modules.

## 8. Diagnostics

Every refused or failing user file will be recorded once per generation, with
its path, error type and a one-line message. The same record will be returned
by:
- the block listing and the type listing;
- `POST /api/blocks/reload` and the MCP `reload_blocks` result;
- the `blocks.reloaded` event.

A block that disappears therefore always comes with its cause.

## 9. Scope And Related Architecture

**In scope.**
- Loading `types/*.py` and `blocks/*.py` from the project tier and the user-library tier, including the tutorial-scoped library.
- Import resolution between those files.
- Type and block lookup by name, and the type identity rule.
- Invalidation and reload.
- Worker parity, and failure reporting.

**Out of scope.**

| Item | Where it belongs |
|---|---|
| Installed plugin packages | They keep loading through entry points and package imports (ADR-052) |
| Scanning user code in a subprocess, and sandboxing it | Issue #1531 |
| Which tiers a tutorial project merges (installed packages leaking into tutorials) | Issue #2480; a registry-composition question independent of loading |
| Package layouts and relative imports for user code | Rejected in Section 11 |

**Related architecture.**
- **ADR-053 personal tool library spec:** defines the tiers this ADR loads from, and FR-012 and FR-016, which this ADR extends.
- **ADR-027:** defines worker reconstruction of typed objects.
- **ADR-054:** defines the panel and MiniApp processes.
- **ADR-055:** covers the standalone MCP bridge and the enterprise edition, which keeps the in-process project switch.

## 10. Verification And Spec Handoff

The implementation must add regression tests that show:
- **One class per type:** a user type imported by a block, reconstructed in a worker and registered by the type registry is one object in each process.
- **The #2480 save succeeds:** a `SimpleSaver` whose input type is a user type saves an object reconstructed by the worker.
- **Sibling imports work:** a block that imports a sibling helper registers and runs.
- **The collision rule applies to every user directory:** stdlib names, installed names and same-tier duplicates are refused with the rename message.
- **Clear-and-reload leaves nothing behind:**
  - after a project switch, nothing from the previous project resolves;
  - after an edit, single-file and package-shaped types both take effect;
  - objects created before a reload still pass the identity rule.
- **Diagnostics match:** every listing and reload response carries the same failure record.
- **Pickling works:** a user-type object pickles in the backend and unpickles in a worker.

The tests extend the files listed in this ADR's `tests` field.

**Spec handoff.** The ADR-053 personal tool library spec
(`docs/specs/adr-053-personal-tool-library.md`) needs these updates:
- **FR-012:** block directories become import roots.
- **FR-016:** the collision rule covers every user directory.
- The loader and the identity rule are recorded as the registration contract.

The owner writes that update.

## 11. Consequences And Alternatives Considered

**Positive consequences**
- Within a generation, a type has one class per process, so strict and name-based checks agree.
- Blocks can share helper code without placing it in `types/`.
- Cleanup has one owner, used by every trigger.
- Pickle and other name-based mechanisms work for user classes.
- Existing projects keep working: `from <type file> import X` is unchanged.

**Negative consequences**
- **Bare names are process-wide.** The collision rule can refuse a file that loads today, for example a helper named after an installed package. The refusal message states the fix.
- **The change is spread out.** It touches the scanner, both registries, the worker payload and every type gate, and lands across several PRs.
- **Reload generations remain.** The name-based identity rule stays necessary for objects created before a reload.

**Alternatives considered**

| Alternative | Why it was not selected |
|---|---|
| Keep synthetic module names and add name-based comparisons wherever a strict check fails | This is today's pattern. Each new gate can reintroduce the failure, and sibling imports stay impossible. |
| One package per user directory with relative imports (`from .scverse_bridge import …`), as ComfyUI and Home Assistant structure extensions | It removes shadowing. It requires package-aware imports that the target users and their agents do not write naturally. |
| Restart the backend on project switch, as Jupyter restarts a kernel | Edits inside a project still need an in-process reload, so the cleanup is needed anyway. A restart also invalidates an open page's WebMCP token. It ends running agent MCP bridge sessions. And the enterprise edition has no supervisor to restart the process. |
| Scan user code in a subprocess and keep only metadata in the backend | It improves isolation and fits issue #1531. It does not change how the worker loads user code. Kept out of scope. |
| Patch classes in place on reload, as IPython `%autoreload` does | IPython documents cases it cannot update. It is unsuitable for a long-lived backend. |
| Synthetic unique names with user directories off `sys.path`, as pytest's `importlib` mode and Airflow's DAG loading do | It avoids collisions, but files cannot import each other and pickling by module name fails. These are the failures this ADR removes. |
