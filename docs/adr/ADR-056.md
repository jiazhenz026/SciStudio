# ADR-056: One Loader For The Python Users Add To SciStudio

## 1. Decision Summary

A scientist who needs something SciStudio does not ship asks the agent to write
it, and what the agent writes is Python placed in the project or in the user's
library. A data type describes the scientist's own kind of data. A block
processes it. A panel or MiniApp carries a `panel.py` that computes what its page
shows. A plot has a render script. These files are written the way a person
writes a notebook: one file imports another by its name. A block that handles
AnnData writes `from scverse_omics import AnnData`, and a helper the agent split
out writes `from scverse_bridge import to_anndata`.

SciStudio loads these files in several places, and each place does it its own
way. The type registry, the block scanner, the worker, format-capability lookup,
the panel process and the plot harness each choose a module name, decide which
directories are importable, and decide what to forget when a file changes. The
same file can therefore exist twice in one process. A block then receives an
`AnnData` built from one copy and checks it against the other: the check fails,
and the error reads "expected AnnData, got AnnData". A helper beside a block
cannot be imported at all, so every block in the importing file disappears. An
edit can leave part of the old code in place. Each of these has been repaired
where it surfaced, and the next consumer written reintroduces it.

This ADR gives every process that runs user code one **user-code loader**. The
loader imports each user file once, under the file's own name, through Python's
import system, as a notebook kernel does (Section 4). It decides which name
belongs to which file and refuses a file whose name would hide a library
(Section 5). Everything that needs user code gets it from the loader by name,
and one rule decides whether two classes are the same data type (Section 6). A
change of any kind is applied by one pass that clears what the loader imported
and loads again, without restarting the backend (Section 7). The backend, the
worker, the panel process and the plot harness all build the same loader
(Section 8). A file that cannot load is reported with its cause wherever users
and agents look (Section 9). Section 2 lists the places user Python lives and
what SciStudio does with each, and Section 3 describes how they are loaded
today.

This ADR builds on the tiers and the drop-in import contract of the ADR-053
personal tool library spec and extends its FR-012 and FR-016 (Section 11). It
keeps ADR-054's panel folder, process and context model and ADR-027's worker
reconstruction. It leaves installed plugin packages to ADR-052, and leaves
running user code outside the backend to the sandbox work of issue #1531.

### 1.1 Problems Addressed

| Problem | Risk | ADR response | Detailed section |
|---|---|---|---|
| User Python lives in several places, and each place is loaded by its own code | Every new consumer brings its own naming, import roots and cleanup, and the inconsistencies surface as unrelated bugs | One user-code loader per process, used for every place user Python lives | Section 4 |
| One user file can be imported twice in a process under different module names | A type check between the two copies fails with "expected AnnData, got AnnData"; port connections and saves have failed the same way | Each file is imported once, under its own name | Section 4 |
| A block cannot import a helper file beside it | The whole file fails to import and all of its blocks disappear | Block directories are importable, like type directories | Section 5 |
| Only type file names are checked against installed libraries | A helper named like a library hides it, or is hidden by it, without any report | One naming rule for every directory the loader serves | Section 5 |
| Each consumer finds user classes and compares types its own way | A new check written with `isinstance` fails on the second copy | One lookup by name and one identity rule for data types | Section 6 |
| Forgetting stale code is spread over several mechanisms, each partial | Edited code, a switched branch or another project's files keep running | One clear-and-load pass for every kind of change | Section 7 |
| The worker, the panel process and the plot harness load user code differently from the backend | Code that registers in the backend behaves differently where it runs | Every process that runs user code builds the same loader | Section 8 |
| A file that fails to load is reported only on the block listing | Blocks vanish while a reload reports that nothing was removed | One failure record, returned by every listing and every reload | Section 9 |

## 2. Users Add Python To SciStudio In Several Places

User Python lives in the project and in the user's library, the same two tiers
the ADR-053 personal tool library spec defines for blocks and types. A tutorial
project reads its library tier from the tutorial-scoped library in place of
`~/.scistudio/`.

| What the user adds | Where it lives | What SciStudio does with it | Where it runs |
|---|---|---|---|
| Data types | `types/*.py`, both tiers | Registers the `DataObject` classes each file defines | Backend, worker, panel process, plot harness |
| Blocks and their helpers | `blocks/*.py`, both tiers | Registers the `Block` classes each file defines | Backend (registration), worker (execution) |
| A panel's or MiniApp's Python | `panels/<panel-id>/panel.py`, both tiers | Starts it as the entry point of the panel process where the context provides `call` (ADR-054 §10) | Panel process |
| Plot render scripts | `plots/<plot-id>/`, project tier | Calls the render entry point inside the plot harness | Plot harness process |
| Legacy previewers | `previewers/*.py`, both tiers | Registers previewer providers, deprecated until 0.3.6 (ADR-054 §8) | Backend |
| Code Block scripts | Anywhere in the project, named by `script_path` | Runs the script as a program in an interpreter the user chooses, exchanging data through files (ADR-041) | A separate interpreter |

The first five are code SciStudio imports into a process it controls, so their
imports are SciStudio's to resolve. A Code Block script is a program: it may run
in an R, MATLAB or foreign Python interpreter, and it receives its data as files.
The loader does not reach into that interpreter (Section 10).

## 3. Each Place Loads Its Code Its Own Way Today

Every consumer in the table below imports user files by path, under a module
name of its own choosing.

| Consumer | Code | Module name |
|---|---|---|
| Block scan | `src/scistudio/blocks/registry/_scan.py` | `_scistudio_dropin_<stem>_<mtime>` |
| Type scan | `src/scistudio/core/types/registry.py` | `_scistudio_type_dropin_<stem>_<mtime>_<hash>` |
| Block instantiation in the backend | `src/scistudio/blocks/registry/__init__.py` | The name recorded on the block spec |
| Format-capability lookup | `src/scistudio/blocks/registry/_capability.py` | A generated name |
| Worker | `src/scistudio/engine/runners/worker.py`, with roots from `src/scistudio/engine/runners/process_handle.py` | The recorded name, loaded again by path |
| Panel process | `src/scistudio/panels/bootstrap.py`, with roots from `src/scistudio/panels/process.py` | `panel` |
| Plot harness | `src/scistudio/plot/_harness.py` | `scistudio_plot_render` |
| Legacy previewers | `src/scistudio/previewers/project.py`, `src/scistudio/previewers/registry.py`, `src/scistudio/previewers/session.py` | Generated names |

While blocks are scanned and run, the type directories are placed on `sys.path`
(`dropin_import_roots` in `src/scistudio/core/dropins.py`), so a block's
`from spectrum import SpectrumData` resolves. That import creates a module named
`spectrum` for a file the type registry has already imported under a generated
name, and the process now holds two `SpectrumData` classes. Some type checks
compare names through `same_registered_type` in `src/scistudio/core/types/base.py`;
others use `isinstance`, and those fail on the second copy.

Block directories are not on the path, so a block file that imports a helper
beside it raises `ModuleNotFoundError` and contributes no blocks. Forgetting old
code is shared out between bytecode eviction, `transient_dropin_modules`, the
collision guard, `refresh_all_registries`, the standalone MCP bridge's
`sync_dropins` and the panel service's watcher, and each forgets a different
subset.

## 4. A User File Is Imported By Its Name, Once Per Process

Each process that runs user code owns one user-code loader. The loader installs
an import finder for user files and resolves names the way Python resolves
names in a notebook's directory: `import scverse_omics` finds
`scverse_omics.py`, executes it once, and keeps it in `sys.modules` under that
name. A package directory with an `__init__.py` is imported the same way.

The type registry and the block registry do not import files themselves. They
ask the loader for the modules in their directories and register the classes
each module defines; a class that one module imports from another is registered
only from the module that defines it. The generated module names go away.
Because the module name of every user class is one the loader can import in any
process, `isinstance`, `issubclass` and pickle agree about user classes within a
process.

The loader imports a file when something first asks for it, and the registries
ask for every file in their directories when they are built. A file the
registries do not scan, such as a helper, is imported when a scanned file
imports it.

## 5. A Name Belongs To One File

The loader answers for a fixed, ordered set of directories, its **roots**. For
every process the shared roots are, in order:

| Order | Root |
|---|---|
| 1 | Project `types/` |
| 2 | Project `blocks/` |
| 3 | Library `types/` |
| 4 | Library `blocks/` |

A process started for one entry point adds that entry's own folder in front of
the shared roots: the panel process adds its `panels/<panel-id>/` folder, and the
plot harness adds its `plots/<plot-id>/` folder. A panel's or plot's helper
files are therefore importable from its entry script and from nowhere else.

The first root that holds a name owns it. A project file therefore takes
precedence over a library file of the same name, which keeps the project-over-
library order of ADR-053. Within one tier a name may belong to one file only: a
project with both `types/utils.py` and `blocks/utils.py` has a conflict, and
neither file loads.

The roots come after the standard library and the installed packages. A user
file whose name is a standard-library module, or the name of an installed
top-level module or package, is refused: it is not importable, it registers
nothing, and its failure record (Section 9) tells the user to rename it. The
installed module keeps resolving to the installed package. This is ADR-053
FR-016 applied to every root.

## 6. Everything Finds User Code Through The Loader

A consumer that needs user code asks for it by name: a data type by its name or
type chain, a block by its type name, a module by its module name. The registries
answer from what the loader imported. No consumer imports a user file by path.

One function decides whether two classes denote the same data type, and it
compares their registered type-name chains. Every place that checks a type
calls it: port compatibility, load and save dispatch, the checks in
`SimpleLoader` and `SimpleSaver`, format-capability matching, and output
validation. Within one process and one load this gives the same answer as
`isinstance`, because each data type has one class. It also gives the right
answer for an object created before the last reload (Section 7), which still
carries the class that existed when it was made.

## 7. A Change Is Applied By Clearing And Loading Again

User code changes when a user or agent saves a file, when a git branch is
switched or a version restored, when a package is installed or removed, when
the user presses Reload or an agent calls `reload_blocks`, and when a different
project is opened. Every one of these runs the same pass:

1. The loader removes from `sys.modules` every module it imported, identified by
   the file it came from, submodules included, and resets its finder.
2. It calls `importlib.invalidate_caches()` and evicts stale bytecode for
   changed files.
3. It reads its roots again, for the project that is now open.
4. The type and block registries and the panel catalog are rebuilt from the
   result.

The backend is not restarted. Restarting on a project switch would spare the
pass for that one trigger, but every other trigger still needs it inside the
running process (Section 12).

A pass starts a new **load**. Objects made before it keep their classes. Anything
that holds such objects across a pass, such as a preview session, a panel
context, a cache or a running workflow, compares types with the rule of
Section 6 and asks the registries again when it needs a class. A worker or panel
process started after the pass imports the new code.

## 8. Every Process That Runs User Code Uses The Same Loader

The backend builds the loader for the open project. Every process it starts to
run user code receives the same ordered roots and builds the same loader before
it imports anything of the user's.

A **worker** imports its block by module name through the loader and
reconstructs its inputs through the registries (ADR-027). The block's own type
checks then see one class per data type.

The **panel process** imports `panel.py` through the loader, with its panel folder
as the first root (ADR-054 §10). A MiniApp's Python can therefore import the
project's data types and its own helper files by name.

The **plot harness** imports the render script through the loader, with its
plot folder as the first root, so a render script can import the project's data
types.

**Legacy previewers** keep their registry until they are removed in 0.3.6
(ADR-054 §8). Their imports of user types resolve through the loader in the
meantime.

## 9. A File That Cannot Load Says Why

The loader records every file it refused or failed to import in the current
load, with the file path, the error type and a one-line message. The same record
is returned by the block listing, the type listing, the panel catalog,
`POST /api/blocks/reload`, the `reload_blocks` tool result, and the
`blocks.reloaded` event. A block, type or panel that is missing after a change
therefore always comes with the reason.

## 10. Scope And Related Architecture

The decision covers the first five rows of Section 2: data types, blocks and
their helpers, panel and MiniApp Python, plot render scripts, and legacy
previewers until their removal. It covers both tiers and the tutorial-scoped
library, the processes of Section 8, the pass of Section 7 and the record of
Section 9.

| Outside this decision | Why | Where it belongs |
|---|---|---|
| Code Block scripts | They run as programs in an interpreter the user chooses, which the loader cannot enter, and they exchange data as files | ADR-041 |
| Installed plugin packages | They are imported as packages through entry points and do not live in the loader's roots | ADR-052 |
| Importing user code outside the backend process | A question of isolation that does not change how a process resolves user code | Issue #1531 |
| Which tiers a tutorial project reads | A question of which registries a project composes | ADR-053 Learning Center spec |
| Panel pages (HTML and JavaScript) | They are served to a sandboxed frame and never imported by Python | ADR-054 §4 |

ADR-053's personal tool library spec defines the tiers and the drop-in import
contract this ADR extends. ADR-054 defines the panel folder, the panel process
and its contexts. ADR-027 defines how a worker rebuilds typed inputs. ADR-017
defines the process handling the worker and panel process already use. ADR-055
defines the standalone MCP bridge, which runs its own loader like any other
process, and the enterprise edition, whose per-user backend switches projects
through the same pass.

## 11. Verification And Spec Handoff

The implementation is verified with regression tests showing that:

- a user data type imported by a block, rebuilt by the worker, used by a panel
  process and registered by the type registry is one class in each process;
- a `SimpleSaver` whose input type is a user data type saves an object the
  worker rebuilt;
- a block that imports a helper beside it registers and runs, and a panel or
  plot imports a helper in its own folder;
- a user file named like a standard-library module or an installed package, and
  a name used twice within one tier, are refused with the rename message;
- after a project switch no module from the previous project resolves; after an
  edit, single-file and package-shaped modules both take effect; an object made
  before a reload still passes the identity rule;
- every listing and reload response carries the same failure record;
- an object of a user data type pickles in the backend and unpickles in a
  worker.

The tests extend the files in this ADR's `tests` field.

The ADR-053 personal tool library spec
(`docs/specs/adr-053-personal-tool-library.md`) takes three changes: FR-012
makes block directories importable, FR-016 applies the naming rule to every
root, and the loader and the identity rule become the registration contract.
The ADR-054 panels spec records that the panel process and plot harness import
through the loader. The owner writes both updates.

## 12. Consequences And Alternatives Considered

A data type has one class in each process within a load, so a check written
with `isinstance` and a check written with the identity rule agree. Blocks,
panels and plots can split code into helper files. What happens after a change
is decided in one place. Pickle works for user classes. A project that imports
its types by file name keeps working unchanged.

A file name now belongs to the whole process. A helper named after an installed
package, which loads today, is refused, and the user renames it. The change
reaches the scanner, both registries, the panel and plot processes, the worker
payload and every type check, so it lands in several pull requests. Objects made
before a reload still carry older classes, which is why the identity rule
compares names.

| Alternative | Assessment |
|---|---|
| Keep generated module names and add name comparisons wherever an `isinstance` check fails | This is the current pattern. Each new check can fail again, and helper files stay unimportable. |
| Give each user directory a package name and require relative imports (`from .scverse_bridge import …`), as ComfyUI and Home Assistant structure extensions | Names never collide with libraries. Scientists and the agents writing for them do not write package-relative imports, and every existing project would need changes. |
| Restart the backend when a different project opens, as a notebook restarts its kernel | Saves, branch switches, package installs and Reload still need the pass inside the running process. A restart also invalidates an open page's WebMCP token, ends running agent MCP sessions, and has no supervisor in the enterprise edition. |
| Import user code only in a separate process and keep metadata in the backend | It isolates the backend, and belongs with issue #1531. The worker, panel process and plot harness still import user code and still need one rule for doing so. |
| Update existing classes in place on reload, as IPython's `%autoreload` does | IPython documents changes it cannot apply. A long-lived backend needs a result it can rely on. |
| Import user files under unique generated names with their directories off the path, as pytest's `importlib` mode and Airflow's DAG loading do | Names never collide. Files cannot import each other, and pickle cannot find classes by module name. |
