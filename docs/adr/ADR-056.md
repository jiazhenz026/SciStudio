# ADR-056: Importing And Reloading User Code Through Python's Import System

## 1. Decision Summary

SciStudio runs Python its users write. Data types in `types/`, blocks in
`blocks/`, a panel's or MiniApp's `panel.py`, plot render scripts, and legacy
previewers live in the project and in the user's library, and the agent writes
most of them. SciStudio has to import this code, run it in several processes,
and replace it when it changes.

That work is spread across more than ten places, and each imports user files in
its own way. Since May 2026 the result has surfaced as more than twenty
incidents: a class that exists twice and fails its own type check, a file that
one process can import and another cannot, code that stays stale after an edit,
a surface that never refreshes, a failure nobody reports, and a file name that
hides a library. Each was fixed where it appeared. Section 2 describes these
incidents, and Section 3 explains how the current code produces them.

This ADR refactors all of that onto Python's own import system, the way a
Jupyter kernel runs a notebook's neighbouring files (Section 4):

- Every process that runs user code puts the user directories on `sys.path`.
- User files are imported by their module names, so each file exists once in `sys.modules`.
- SciStudio adds only what Python leaves out: a check that refuses file names that would hide a library, and a reset that forgets user modules and imports them again when anything changes.

Section 5 lists the incidents this removes, the new problems it introduces, and
how those are handled. Section 6 describes what changes for a person writing
blocks, types, panels and plots, and what stays compatible.

This is a refactor of how SciStudio treats user code. It changes the drop-in
import contract of the ADR-053 personal tool library spec (FR-012, FR-015,
FR-016) and keeps ADR-054's panel model and ADR-027's worker reconstruction.

### 1.1 Problems Addressed

| Problem | Risk | ADR response | Detailed section |
|---|---|---|---|
| Importing and reloading user code is scattered across more than ten places, each with its own rules | The same classes of bug recur with every new consumer | One import path through Python's import system and one reset | Section 2 |
| One user file is imported under several module names | A class fails its own type check ("expected AnnData, got AnnData") | Import every user file under its own module name | Section 3 |
| What is importable differs by consumer and by process | Code registers in the backend and fails in the worker, or a helper file cannot be imported | The same `sys.path` roots in every process | Section 4 |
| Stale code survives edits, branch switches and project switches | Old code keeps running with no sign of it | One reset that forgets all user modules and imports them again | Section 4 |
| Each surface has its own refresh trigger | A block, type or panel is missing until an unrelated action happens | One reset entry point for every trigger | Section 4 |
| Failures are swallowed or misreported | A block disappears while a reload reports nothing removed | One failure record returned by every listing and reload | Section 5 |
| File names can hide or be hidden by libraries | A helper silently replaces a library, or is replaced by it | One name check for every user directory | Section 5 |
| Users need to know what the refactor changes for them | Existing blocks break, or new abilities go unnoticed | A compatibility statement for every kind of user file | Section 6 |

## 2. Importing And Reloading User Code Is Scattered Across SciStudio

Each incident below was fixed where it surfaced. Together they show six recurring
problems. Numbers are issues and the pull requests that fixed them; #2481 is open.

| Recurring problem | Incidents | What users saw | How each was fixed |
|---|---|---|---|
| **A.** One file is imported under several module names, so a class exists twice | #706 (PR 715), #1374 (PR 1561), #1950 (PR 1951), #2134 (PR 2155), #2480 | A drop-in block failed in the worker with an unknown module name. `save_data` refused valid edges. | **B.** What can be imported differs by consumer and by process | #1332, #1343, #1365 (PRs 1339, 1386), #1752 (PR 1754), #1772 (PR 1774), #1885 (PR 1939), #1950, #2022 (PR 2035), #2480 | Project and library types were never scanned, then failed to resolve. The fixes resemble each other because the problems are one problem. Every place
that needs user code decides for itself how to import it, what else should be
importable, and when to forget it. A fix repairs one place, and the next place
written makes the same decision again.

## 3. Why It Happens: How SciStudio Imports User Code Today

SciStudio imports user files by file path, under module names it makes up, and
treats `sys.path` as something to change briefly around each import.

| Where | What it does |
|---|---|
| Block scan, `blocks/registry/_scan.py` | Runs the name guard, then executes each `blocks/*.py` by path as `_scistudio_dropin_<stem>_<mtime>` inside a window that prepends the type directories to `sys.path`. The module is not added to `sys.modules`. |
| Type scan, `core/types/registry.py` | Executes each `types/*.py` by path as `_scistudio_type_dropin_<stem>_<mtime>_<hash>` and adds that name to `sys.modules`. |
| Block instantiation, `blocks/registry/__init__.py` | Runs the guard again and executes the block file by path again. |
| Capability lookup, `blocks/registry/_capability.py` | Executes the block file by path again. |
| Worker, `engine/runners/worker.py`, `engine/runners/local.py`, `engine/runners/process_handle.py` | Adds the roots it was given to `sys.path` for good, then executes the block file by path under the name recorded by the scan. |
| Guards and eviction, `core/dropins.py` | Build several root sets. Install a refusing finder on `sys.meta_path`. Delete a type's bare module from `sys.modules` on every guard call. Evict modules added inside a window. Evict stale bytecode. |
| Path window, `desktop/paths.py` | Prepends roots to `sys.path` and `PYTHONPATH` for the length of a `with` block. Also used by `core/entry_points.py` and `blocks/io/_unified_dispatch.py`. |
| Legacy previewers, `previewers/*.py` | Execute files by path inside a window, and evict what the window added. |
| Panel process, `panels/bootstrap.py`, `panels/process.py` | Adds the panel folder to `sys.path` and executes `panel.py` by path as `panel`. |
| Plot harness, `plot/_harness.py` | Executes the render script by path as `scistudio_plot_render`. |
| Reload drivers | `refresh_all_registries` (`api/runtime/_projects.py`), the save hook (`api/runtime/_file_writes.py`), `hot_reload`, the standalone MCP bridge's `sync_dropins` (`ai/agent/mcp/runtime.py`), and the panel watcher (`panels/watcher.py`). |

This produces each recurring problem of Section 2:

- **A. Duplicate classes.** A block's `from scverse_omics import AnnData` imports `types/scverse_omics.py` again under its plain name, after the type scan imported it under a generated one. The process now holds two `AnnData` classes. Type checks compare classes by identity in some places (`simple_io.py`, `collection.py`, `composite.py`, `savers/_capability.py`) and by name in others (`same_registered_type`, `TypeSignature.matches`), so whether a check passes depends on which copy it was handed.
- **B. Uneven import roots.** Each call site assembles its own roots and opens its own window, so a file that one consumer can import is invisible to another. Block directories are in no root set.
- **C. Stale code.** The generated names embed a timestamp, so every scan creates new module objects and leaves the old ones behind. Forgetting stale code is spread over a window, a guard side effect and a bytecode step, and each covers a different part.
- **D. Separate refresh triggers.** Five reload drivers each rebuild a different subset of registries.
- **E. Failures swallowed or misreported.** Every call site catches import failures on its own, and only the block listing collects them.
- **F. Name collisions.** The collision guard exists for type files only, and it has to intercept imports because it cannot keep names off `sys.path` while roots are prepended.

## 4. Solution: Python's Import System, As A Jupyter Kernel Uses It

A Jupyter kernel makes the files beside a notebook importable by putting that
directory on `sys.path` at startup. From then on it relies entirely on Python's
import system: `import helper` finds `helper.py`, runs it once, and keeps it in
`sys.modules`. A kernel restart is the reliable way to pick up changed code, and
the optional `%autoreload` extension checks file modification times before each
cell. SciStudio adopts the same route. The names used below follow Python's
vocabulary: the **user import path** is the set of user directories on
`sys.path`, and the **user module reset** is the step that forgets user modules
so they are imported again.

### 4.1 The User Import Path

The user import path is an ordered list of directories:

| Order | Directory |
|---|---|
| 1 | The entry folder of the process, when there is one: `panels/<panel-id>/` for a panel process, `plots/<plot-id>/` for a plot render |
| 2 | Project `types/` |
| 3 | Project `blocks/` |
| 4 | Library `types/` (the tutorial-scoped library for a tutorial project) |
| 5 | Library `blocks/` |

Every process that runs user code appends this list to the end of `sys.path`,
after the standard library and the installed packages, and leaves it there.
This applies to the backend, the worker, the panel process and the plot
harness. The backend does this when a project opens. A process SciStudio starts
receives the list in its environment, as `multiprocessing` passes `sys.path` to
a spawned child. No call site opens a temporary window, and no finder is
installed on `sys.meta_path`.

### 4.2 Importing User Code By Name

A user file is imported with `importlib.import_module(<file stem>)`, and a
package directory with an `__init__.py` by its directory name. Python finds it
through `sys.path`, executes it once, and stores it in `sys.modules`. The type
registry and the block registry list the files in their directories, import each
module by name, and register the classes each module defines. A class a module
imported from another module is registered only from the module that defines it.

The worker imports its block by module and class name. The panel process imports
`panel`, and the plot harness imports the render script by its module name. No
code executes a user file by path, and the generated module names are retired.
Every user class therefore has a module name any of these processes can import,
which is also what pickle requires.

### 4.3 Names On The User Import Path

Before a directory is used, each file stem in it is checked:

- A stem in `sys.stdlib_module_names` is refused.
- A stem that `importlib.util.find_spec` resolves outside the user import path, to an installed module or package, is refused.
- A stem that appears in more than one directory of the same tier is a conflict, and every file with that stem is refused.

A refused file is not imported and registers nothing, and its failure record
(Section 5.3) asks the user to rename it. Across tiers the order of Section 4.1
decides, so a project file takes precedence over a library file with the same
stem.

### 4.4 The User Module Reset

The backend changes user code without restarting (owner decision, 2026-09-16).
A single entry point performs the reset:

1. Collect every module in `sys.modules` whose `__file__` lies under a directory
   of the current or previous user import path, including submodules.
2. Remove those modules from `sys.modules`, delete their stale bytecode, and call
   `importlib.invalidate_caches()`.
3. If the project changed, replace the user import path on `sys.path`.
4. Rebuild the type registry, the block registry and the panel catalog by
   importing again (Section 4.2).

All triggers call this entry point: a file saved through the app, a change seen
by a watcher or by the standalone MCP bridge, a git branch switch or version
restore, a package install or removal, the Reload action, the `reload_blocks`
tool, and opening another project. Before resetting, the entry point compares
the modification times of the user files with those recorded at the last
import, as `%autoreload` does, and does nothing when nothing changed.

The reset forgets every user module, including unchanged ones. `%autoreload`
reloads only changed modules and patches the old classes in place, and its
documentation lists cases that patching cannot handle. A block module that
imported a type holds a reference to the old class, so reloading only the
changed type module would bring back the duplicate classes of Section 3.
Forgetting all user modules gives the same result as a kernel restart for user
code, without restarting the backend.

A worker and a plot render run in a new process each time, so they always import
current code. A MiniApp's panel process is resident. It is restarted through the
existing panel process restart (ADR-054 §10) when a reset changes a module it
imported.

### 4.5 One Type Identity Rule

Objects created before a reset keep their classes. A preview session, a panel
context, a cache or a running workflow can hold such an object and compare it
with a class from the new import. Every type check therefore uses one function,
which compares registered type-name chains:

- port compatibility;
- load and save dispatch;
- the `SimpleLoader`, `SimpleSaver`, `Collection` and `CompositeData` checks;
- format-capability matching;
- output validation.

Within one import this agrees with `isinstance`, because each data type has one
class.

### 4.6 What The Refactor Removes

The generated module names and every by-path execution in Section 3 are removed,
together with:

- the `sys.path` window;
- `transient_dropin_modules`;
- the guard's deletion of bare modules;
- the refusing finder on `sys.meta_path`;
- the file path stamped on block classes for the worker;
- the separate reload drivers, which become callers of the reset entry point.

Bytecode eviction moves into the reset.

## 5. What The Refactor Fixes, And What It Introduces

### 5.1 Fixed

| Recurring problem | Why it stops |
|---|---|
| A. Duplicate classes | Each user file exists once in `sys.modules` of each process, and every check uses one identity rule |
| B. Uneven import roots | Every process has the same user import path, which includes block directories |
| C. Stale code | The reset forgets every user module by file location, submodules included, and generated names no longer accumulate |
| D. Separate refresh triggers | Every trigger calls the same reset, which rebuilds every registry |
| E. Failures swallowed or misreported | Section 5.3 |
| F. Name collisions | Section 4.3 applies to every user directory, before anything is imported |

### 5.2 Introduced, And How Each Is Handled

| New problem | Handling |
|---|---|
| User module names are now process-wide, so a stem can clash with a library | Section 4.3 refuses the file and tells the user to rename it |
| The user import path stays on `sys.path` for the backend's lifetime, so a later import anywhere in the process could reach a user file | User directories come after the standard library and installed packages, and refused stems are never importable, so an import that resolved before still resolves to the same module |
| Objects made before a reset carry older classes | Section 4.5 |
| A module's top-level code runs again on every reset, and resets happen on every change | Resets are skipped when no user file changed. Top-level code is expected to define things, as in any importable module. Failures are recorded (Section 5.3). |
| A resident panel process keeps old code after a reset | It is restarted when a module it imported changed (Section 4.4) |
| The standalone MCP bridge and the backend are separate processes and each holds user modules | Each runs the reset on its own triggers; both read the same directories |
| Forgetting all user modules costs more than reloading one | The number of user files per project is small, and the reset runs only on changes |

### 5.3 One Failure Record

The import step records every refused or failed user file, with its path, the
error type and a one-line message. The same record is returned by:
- the block listing, the type listing and the panel catalog;
- `POST /api/blocks/reload` and the `reload_blocks` tool result;
- the `blocks.reloaded` event.

The reload diff compares the registries before and after the reset.

## 6. What Changes For Users

A person, or the agent working for them, writes user code the way they write
code beside a notebook.

| Writing | Before | After | Compatible |
|---|---|---|---|
| A block importing a type: `from scverse_omics import AnnData` | Works | Works | Yes |
| A block importing a helper beside it: `from scverse_bridge import to_anndata` | Fails, and every block in the file disappears | Works | New ability |
| A block importing another block file | Fails | Works; the imported block is still registered only from its own file | New ability |
| A type importing another type file | Works | Works | Yes |
| A panel's `panel.py` importing a type or a helper in its folder | Helpers in its folder work; types work through the panel import roots | Works | Yes |
| A plot render script importing a type or a helper in its folder | Not guaranteed | Works | New ability |
| A user file named like a standard-library module or an installed package | Refused for type files; loaded for block files | Refused for every user file, with a rename message | Breaking for block, panel and plot helper files with such names |
| The same stem in `types/` and `blocks/` of one tier | Both loaded, under different names | Both refused, with a rename message | Breaking for such projects |
| A module's `__module__` and pickled class paths | A generated name such as `_scistudio_type_dropin_…` | The file's own name | Yes for users; pickles written under generated names are not read back |
| Package-shaped types (`types/<name>/__init__.py`) | Loaded; submodules could stay stale | Loaded; submodules are reset with the package | Yes |
| Relative imports between user files | Not supported | Not supported; files import each other by name | Yes |
| An edit taking effect | On whichever refresh the surface had | On the next reset, which every trigger runs | Yes |
| Code Block scripts | Run as programs in the chosen interpreter | Unchanged (Section 7) | Yes |

The agent's skills and the user guide describe these rules; the owner updates
them.

## 7. Scope And Related Architecture

The refactor covers:
- data types, blocks and their helper files, `panel.py`, plot render scripts, and legacy previewers until their removal in 0.3.6;
- both tiers and the tutorial-scoped library;
- the backend, the worker, the panel process, the plot harness and the standalone MCP bridge.

| Outside this refactor | Reason | Where it belongs |
|---|---|---|
| Code Block scripts | They run as programs in an interpreter the user chooses, and exchange data as files | ADR-041 |
| Installed plugin packages | They are imported as packages through entry points | ADR-052 |
| Running user code outside the backend process | An isolation question; it does not change how a process resolves user code | Issue #1531 |
| Which tiers a tutorial project composes | A question of which registries a project reads | ADR-053 Learning Center spec |
| Panel pages (HTML and JavaScript) | Served to a sandboxed frame and never imported by Python | ADR-054 §4 |

ADR-053's personal tool library spec defines the tiers and the drop-in import
contract this ADR replaces. ADR-054 defines the panel folder and the panel
process. ADR-027 defines how the worker rebuilds typed inputs. ADR-017 defines
process handling for the worker and panel process. ADR-055 defines the
standalone MCP bridge and the enterprise edition, whose per-user backend
switches projects through the same reset.

## 8. Verification And Spec Handoff

Regression tests show that:
- a user data type is one class across a block, the type registry, the worker and a panel process;
- the `SimpleSaver` failure of #2480 no longer occurs;
- a block imports a helper and another block file beside it, and a panel and a plot import a type and a helper in their folders;
- the name check refuses stdlib stems, installed stems and same-tier duplicates;
- after a project switch no module from the previous project resolves;
- after an edit, single-file and package-shaped modules both take effect, and an object made before the reset still passes the identity rule;
- a resident panel process restarts when a module it imported changes;
- every listing and reload response carries the same failure record, and the reload diff is correct;
- an object of a user type pickles in the backend and unpickles in a worker.

The tests extend the files in this ADR's `tests` field.

Two specs need updates:
- **The ADR-053 personal tool library spec:** FR-012, FR-015 and FR-016 are rewritten around the user import path, the name check and the failure record.
- **The ADR-054 panels spec:** records that the panel process and the plot harness import through the user import path.

The owner writes both updates.

## 9. Alternatives Considered

| Alternative | Assessment |
|---|---|
| Keep the current design and add a name fallback wherever an identity check fails | This is the pattern of Section 2. It fixes one call site at a time, and helper files stay unimportable. |
| A custom import hook on `sys.meta_path` that serves user files under SciStudio-chosen names | It rebuilds what `sys.path` already does and keeps two notions of a module's name. |
| Give each user directory a package name and require relative imports, as ComfyUI and Home Assistant structure extensions | It avoids name clashes. The users and the agents writing for them do not write package-relative imports, and every existing project would change. |
| Restart the backend to pick up changes, as a notebook kernel restarts | Saves, branch switches, package installs and Reload would each cost a backend start. A restart also invalidates an open page's WebMCP token and ends running agent MCP sessions, and the enterprise edition has no supervisor to restart the process. |
| Reload only changed modules and patch old classes in place, as `%autoreload` does | Modules that imported the changed one keep old references, and patching has documented gaps. |
| Import user files under unique generated names with their directories off `sys.path`, as pytest's `importlib` mode and Airflow's DAG loading do | Names never clash. Files cannot import each other, and pickle cannot find classes by module name. |
| Import user code only in a separate process and keep metadata in the backend | It isolates the backend and belongs with issue #1531. The worker, panel process and plot harness still need the same import rules. |
