# ADR-054: Explore Sessions And One Contract For Interactive Panels

## 1. Decision Summary

A scientist runs the first three blocks of a workflow, looks at what came out,
and does not yet know what the fourth block should be. Finding out means trying
things: filtering on a column to see whether the effect survives, changing a
threshold to see how many peaks it keeps, plotting one channel against another
because a colleague mentioned it. None of this is known in advance, which is
precisely why it is being done.

SciStudio currently asks this user to declare the answer before they have it.
Building an interactive block means designing its parameters and its panel up
front. Writing a Code Block means knowing which transformation to write. Both
are reasonable once the analysis is understood, and both are the wrong shape
for the hour that precedes understanding. Users respond the way the incentives
suggest: they leave SciStudio, explore in a notebook they already have, and
come back with a conclusion whose derivation now lives outside the product.
Nothing that happened in that hour is recorded, and the workflow that results
carries no trace of the reasoning that produced it.

This ADR introduces the **Explore Session**: a notebook-backed workspace opened
from a block's output, in which the user manipulates that data through
interactive panels and through code, and out of which a Code Block can be
produced. Its organising commitment is that **every change a user makes to the
data becomes a line of code in the notebook**, so the record of what was tried
exists without the user maintaining it.

Six decisions follow from that commitment and from the surfaces SciStudio
already has.

An Explore Session is a new file created from one block output, and the
notebook's first cell loads that output by reference, which makes the notebook
replayable from a cold kernel and portable outside the product.

Interactive panels stop having a loading path each. The previewer loader, the
interactive-block panel loader, and the one an Explore Session would otherwise
add collapse into one contract with negotiated capabilities, authored as
self-contained HTML documents in sandboxed frames, which is the form an agent
writing a panel on a user's behalf can test and fail at safely.

The session runs a resident kernel on the application's own bundled Python, so
an analysis that works during exploration works after promotion.

Cells execute in the order they are written, and the system re-runs the cells
that depend on a cell the user changed, which removes the stale-result hazard
without removing the ability to reuse a variable name.

A SciStudio block can be called from a notebook cell and executes inside the
kernel. Such a cell records its provenance in full, and it maps onto a workflow
node without interpretation when the session is promoted.

Each cell run is committed, and each cell run that produces a persisted object
writes a lineage record anchored on the session rather than on a workflow run.

### 1.1 Problems Addressed

- Exploratory analysis has no home in SciStudio, so it happens elsewhere and
  its derivation is lost.
- Interactive blocks require the user to know the shape of the interaction
  before the analysis is understood.
- Two near-identical dynamic module loaders already exist with separate
  versioning, asset routing, and failure behaviour, and exploration would add a
  third.
- Work done in an external notebook cannot become a workflow without being
  rewritten.

## 2. An Explore Session Starts From Data That Already Exists

An **Explore Session** is a notebook, a resident Python kernel, and a set of
interactive panels bound to variables in that kernel. It is created from the
output of one block on the canvas, and it exists to let the user do anything
they want with that output.

The session is a **new file**. It is not a second rendering of the workflow it
came from, and promoting it later is a real conversion rather than a change of
view. This matters because the two objects have different shapes: a workflow is
a graph of declared blocks with typed ports, and an Explore Session is a
sequence of statements over live objects, most of which will be discarded.
Treating them as one object would force the exploratory half to carry the
workflow's declaration burden, which is the burden this ADR exists to remove.

Creation captures the block output as a **data reference**, and the notebook's
first cell loads it:

```python
df = scistudio.load("<ref>").to_pandas()
```

Writing the load into the notebook rather than injecting a variable behind the
user's back is what makes everything downstream work. The notebook replays from
a cold kernel, so a crashed or restarted kernel is recovered by re-running
rather than by special machinery. The notebook opens in Jupyter or Colab and
still describes its own inputs. Promotion has a complete script to package
rather than a script with an invisible first step. Each of these would need
separate handling if the first cell were implicit.

The kernel holds **native objects**. `df` is a `pandas.DataFrame`, an array is a
`numpy.ndarray`, and the SciStudio type layer supplies the conversions at the
boundary — `DataObject.to_memory()`, `DataFrame.to_pandas()`, `Array.to_numpy()`
on the way in, and construction from `data=` on the way out. The alternative,
handing the user SciStudio's own wrapper types, would make every line of
generated code unfamiliar and would put a translation step in front of
promotion. Users of this feature know pandas; the product gains nothing by
standing between them and it.

### 2.1 The Session Is A Tab, And The Notebook Replaces The Preview

The frontend already models the centre area as a discriminated union of tabs —
`WorkflowTab | FileTab | PreviewTab`, where the preview tab was added by #2112.
An Explore Session adds one more member to that union. When an Explore tab is
active, the right-hand pane renders the session's notebook in place of the data
preview, and the left-hand pane is unchanged.

This is a deliberately small structural change. An Explore Session is a way of
working on a project that is already open, and giving it a wholly separate
application layout would separate it from the palette, the project tree, and
the card panels the user needs while exploring. Discovery of the blocks that
can be called from a cell is served by adding a card to the existing card
panel.

Inside the Explore tab, a secondary view renders the session's **dependency
graph** — one node per variable version, edges from the analysis described in
§5. The linear notebook cannot show that two filters are siblings rather than
successive steps, cannot show which results a pending re-run will invalidate,
and gives a subgraph selection nowhere to live. The graph also happens to be
the shape the session will take when it is promoted, so a user watching it grow
is being told in advance what promotion will produce.

## 3. One Contract Serves Every Interactive Panel

SciStudio has three dynamic panel loading paths. The previewer loader validates
a manifest, imports an ES module from a backend-validated same-origin URL,
reads a named export, checks an API version, and mounts it with a read-only host
API (`dynamicPreviewer.ts`, ADR-048 FR-022/FR-023). The interactive-block panel
loader does the same sequence against a different asset route and hands the
module `confirm`/`cancel` instead (`panelModuleLoader.ts`, ADR-051). An Explore
Session needs a third, which would differ from both only in what the host hands
over.

How a panel is **found** already differs legitimately between the two, and this
ADR leaves that alone. A previewer is routed by the type of the data being
shown, so it needs the ladder that resolves project over user over package over
core across exact and ancestor matches (`previewers/router.py`) together with a
per-type user choice (#2017, #2049). An interactive block's panel is named by
its block — `InteractiveMixin.interactive_panel` is a `PanelManifest` declared
on the class — so it is discovered exactly as its block is, inherits the block
tiers including the user library, and has no routing question to answer. An
Explore panel is routed by the type of the variable it binds, which puts it on
the previewer ladder.

What has diverged without cause is everything **below** that: two copies of the
load sequence, two API version constants, two asset whitelists, and two
different things happening when a module fails to load. A third copy would make
it three.

The loaders collapse into **one contract with negotiated capabilities**. A panel
declares what it is; the host supplies a bounded set of primitives; the same
document shape serves all three uses. A read-only previewer receives no write
path of any kind. An interactive-block panel additionally receives `confirm` and
`cancel`. An Explore panel additionally receives variable bindings and
`emitCode`. Each use keeps the discovery mechanism appropriate to it and shares
the loading, versioning, and failure behaviour that none of them had a reason to
own separately.

### 3.1 A Panel Is A Self-Contained HTML Document In A Sandboxed Frame

The unified contract's authoring form is **one self-contained HTML file** —
markup, styles, and script in a single document — mounted in a sandboxed
`iframe` and reachable only through `postMessage`.

The form is chosen for who writes these panels. A panel that ships with a
package is written once by a package author, and a panel belonging to a project
or a user library is, in practice, written by the agent on the user's behalf;
ADR-053 §4 records the same conclusion for blocks, and there is no visual panel
editor planned. Authoring by an agent has two requirements that dominate every
other consideration. The agent must be able to **see whether its output works**,
which a plain HTML file satisfies by opening in a browser with stub data and
which no kernel-coupled widget format satisfies. And the agent's first attempt
must be able to **fail without consequence**, which the frame boundary provides:
a runaway loop, a leaked global handler, or a thrown exception is contained in
the panel that caused it. Plain HTML is also the single most widely represented
UI form there is, so the agent writes it from a far deeper well of examples than
any framework-specific alternative offers.

The frame boundary carries a second benefit that grows with session length.
Explore Sessions run for hours with several panels mounted, and a panel that
leaks memory, captures the keyboard, or bleeds CSS into the application would
degrade the whole workspace if it shared a realm with it. Containment costs
nothing extra once the boundary exists for authoring reasons.

The cost accepted in exchange is that **panels render only inside SciStudio**. A
notebook carried to JupyterLab or Colab still executes every line of its code
and still describes its own inputs; what it loses is the interactive surface,
which is SciStudio's own contribution rather than something the user brought
with them. Storing notebooks as `.ipynb` (§7) delivers portability of the
analysis; the panels were never portable value.

Because the frame has no shared realm with the kernel, a panel has exactly one
outbound path for anything it wants to change: `emitCode`, which appends a cell
and executes it. The guarantee this ADR is built on therefore holds structurally
rather than by the discipline of panel authors — there is no second channel to
misuse.

`emitCode` resolves with the new snapshot and marks the update as originating
from the calling panel, so a panel can distinguish its own edit from a change
made elsewhere and keep its selection rather than resetting it. Without this,
every user click would clear the selection the click was made from.

### 3.2 What The Host Supplies

Across the `postMessage` boundary the host hands a panel its bindings — a map
from variable name to type and current snapshot — along with a bounded windowed
read (`getView`), the capability primitives its declaration earned, an update
callback carrying the reason and the changed bindings, and an error channel.
Panels bind **multiple variables**, because comparing a spectrum against a table
is the ordinary case rather than an advanced one.

Message passing costs little here because the contract is already asynchronous
end to end: a windowed read is a server round trip, `emitCode` waits on the
execution queue, and updates arrive as pushes. Only the opening snapshot is
synchronous, and it is delivered once at mount.

Reads are windowed for the same reason previews are: a bound variable may be
larger than the frontend can hold. The existing bounded data-access layer under
`scistudio.previewers.data_access` supplies the mechanism, so the panel receives
the page it is displaying rather than the object. A panel that needs bulk data —
an image plane, a long trace — fetches it from the same-origin asset route
directly, which keeps large payloads out of both the message channel and the
application's own memory.

## 4. The Kernel Runs On The Application's Own Python

The session's kernel is an `ipykernel` process launched from SciStudio's
**bundled Python**, the same interpreter and the same dependency set the
workflow runtime uses.

The failure this avoids is specific and expensive: an analysis that works during
exploration and fails after promotion. A user who discovers that their explored
pipeline does not run as a block has been given a reason to distrust the
promotion path, which is the path this ADR is built around. Sharing the
interpreter removes the class of divergence entirely.

Using `ipykernel` rather than a bespoke execution loop follows from who the
users are. They know Jupyter, which means they expect `%pip`, `%%time`, and the
rest of the magic vocabulary to work, and they will type them whether or not
they are supported.

Two known costs are inherited and must be handled rather than discovered later.

Bundled-runtime dependency drift becomes more visible. Reusing
`resources/python` omits dependencies added to `pyproject.toml` after it was
built, and OTA updates cannot ship runtime dependencies. Exploration will make
users encounter missing libraries far more often than workflow execution does,
because exploring is when people reach for something new.

The install path must lead to the right environment. The embedded terminal's
default-to-conda-base defect was fixed for zsh and bash by #1838, and an Explore
Session should not depend on that fix holding for every shell. The session
offers installation through the kernel's own `%pip`, which by construction
installs into the environment the kernel is running in.

An Explore Session **modifies its own environment**, which workflow runs do not.
An `EnvironmentSnapshot` captured once at session start stops describing the
session as soon as the user installs something. Snapshots are therefore taken
per durable execution rather than per session, and stored by reference so that
a full `pip freeze` is not duplicated into every record (§8).

## 5. Cells Execute In Written Order, And Dependents Re-Run

Classic notebook semantics let a user edit a cell, re-run it, and leave every
downstream cell displaying results computed from the previous value, with
nothing on screen indicating that this has happened. For a user who has not
built the habit of restarting and running everything, the consequence is a
conclusion drawn from a stale number. In a scientific setting this is a
correctness problem rather than an inconvenience.

Reactive notebooks solve it by deriving a dependency graph over cells and
re-running dependents. The well-known implementation of this idea forbids
defining the same variable in two cells, because its graph is keyed on global
variable names and two definitions make a reference ambiguous. That constraint
is unacceptable here: the users this feature targets are Jupyter-fluent, and
`df = df.dropna()` is how they write.

Both properties are available together by keeping **written order** as the
authority and versioning each assignment:

```python
[1] df = load(ref).to_pandas()        # defines df@1
[2] df = df[df.intensity > 100]       # reads df@1, defines df@2
[3] peaks = find_peaks(df)            # reads df@2, defines peaks@1
```

With order fixed, `df` in any cell refers unambiguously to the nearest
definition above it, so the graph is exact and variable names are reusable. What
this model gives up relative to the name-keyed one is position independence —
cells cannot be reordered arbitrarily and have the system recover their intended
order. Notebooks are read top to bottom, so the loss is theoretical.

The graph earns three things beyond correctness. It tells the panel layer
exactly which bindings changed, which removes the need to detect mutation in
Python, where `df is not old_df` misses every in-place modification. It bounds
the freeze in §5.2 to the panels a pending re-run can affect. And it is the
structure promotion translates, which is why §9 is short.

The analysis is built on the standard library's `ast` module: per cell, the
names bound (assignment targets, augmented assignments, loop targets, `with ...
as`, imports, function and class definitions) and the names read freely, joined
in written order. No third-party dependency is required. Magic lines are not
valid Python, so IPython's input transformer rewrites them into ordinary calls
before the analysis runs.

The model has a real limit. `df.dropna(inplace=True)` rebinds nothing, so static
analysis sees no new version and the edge is missed; aliasing (`df2 = df`
followed by mutation of `df2`) fails the same way. Panel-generated code always
rebinds and never mutates in place, which covers the majority of cells in
practice. Hand-written in-place mutation is flagged where it can be recognised.
No dependency model available in Python handles this case, so the honest
position is to bound it rather than to claim it away.

### 5.2 One Execution Queue Removes The Need For A Lock

A panel edit and a hand-run cell can never race, because both are submitted as
executions to a kernel that has one execution queue. Nothing needs to be locked;
the ordering falls out of the queue. The consequence worth stating is that the
notebook's cell-run sequence is a total order over every change to the session's
data, whatever its origin, which is why reproducibility does not depend on user
discipline.

What does need design is what the interface does while an execution is in
flight.

The freeze is **shallow**. A cell may run for minutes, and during that time the
panel continues to zoom, pan, page, and switch views, because it is displaying a
snapshot and reading a stale snapshot harms nothing. What suspends is the
ability to submit a new edit. A greyed-out panel would make the session's
primary surface unusable for much of its life.

The freeze is **symmetric**. Code emitted by a panel occupies the queue exactly
as a hand-run cell does, and the notebook waits behind it under the same
indicator.

The freeze has an **exit**. A hung cell must be interruptible, and the interrupt
must actually reach the kernel. This is called out as a requirement because the
product has previously shipped a stop control that did not stop what the user
believed it stopped (#1790).

## 6. A Block Call Is A Different Kind Of Step Than A Line Of Python

A notebook cell may call a SciStudio block:

```python
peaks = blocks.run("imaging.find_peaks", img=img, sigma=2.0)
```

The call **executes inside the kernel**. A thin adapter performs what the
workflow runner performs around a block — port validation, wrapping native
objects into typed `DataObject`s on the way in and unwrapping on the way out,
and translating block exceptions — and returns a native object. Routing the call
through the real runner instead would spawn a subprocess per call and produce a
reference to load back, which is the wrong latency for a surface whose purpose
is rapid iteration. Executing in-kernel forfeits subprocess isolation, so a
block that crashes the interpreter takes the kernel with it; the kernel is
restartable and the notebook replays, and Code Blocks and App Blocks spawn their
own processes regardless, which leaves process blocks as the only genuinely
in-process case.

The consequence that matters is that the notebook now contains **two kinds of
step**. A block call is self-describing: block identifier, version, and resolved
parameters are structured data. A line of pandas is replayable and otherwise
opaque. The distinction propagates into provenance (§8), where a block call
records what a workflow node records, and into promotion (§9), where a block
call maps onto a node with nothing to interpret. It gives a user who cares about
the traceability of a step a concrete reason to reach for a block, without
forbidding them anything.

Interactive blocks called from a cell resolve through the panel contract of §3.
A block that pauses for input has its panel rendered by SciStudio's own
surface — as a modal during a workflow run, and in the session's panel area
during exploration — from one module in both cases. The signalling path is the
one interactive blocks already use between the runtime and the frontend, so the
notebook's display protocol is not involved. This convergence is the reason the
migration in §10 refactors panels before building the session.

A cell that calls an interactive block therefore only completes inside
SciStudio; run elsewhere, it waits for a panel that will not appear. This
follows from §3.1 and is stated so that promotion and any future notebook import
can recognise such cells rather than discover them.

Two supporting concerns are noted rather than resolved here. Block versions
recorded in a cell may drift from the installed block, which is the same problem
workflow lineage has and should take the same answer rather than a second one.
And the parameters available for a given block need to be discoverable from
inside the session, which the card panel serves.

## 7. Every Cell Run Is Committed

A session's notebook is stored as **`.ipynb`**. The format is the one these
users already know, it opens in every notebook tool they might carry it to, and
it keeps open the possibility of bringing a user's existing notebooks in. It
also carries an official per-notebook metadata field, which gives the dependency
graph of §5 a place to be cached that other tools will ignore.

What is committed has its **cell outputs stripped**. Outputs are execution
state, and ARCHITECTURE.md §4.6 already keeps runtime state and large data out
of ordinary commits; in an Explore Session they are additionally redundant,
because anything durable is already a reference recorded in §8. The file on disk
keeps its outputs, so a user who opens the notebook in Jupyter or sends it to a
colleague still sees results. Stripping happens on the way into git.

Each cell run appends a commit containing the notebook at that moment. The user
takes no action, and the history exists because it was never optional.

Measurement decides the shape of the implementation. On the path SciStudio
actually uses — the bundled git binary invoked as `add` then `commit` through
`GitEngine` — a commit of a fifty-cell notebook costs **27–31 ms**, and a
worktree carrying two thousand tracked files does not change that materially
because git's index stat cache absorbs it. Loose objects accumulate at roughly
12 KB per commit and compress by about twenty-five times when packed, so a
thousand cell runs occupy under a megabyte of packed history.

Storage is therefore not a constraint, and the cost that remains is latency in
the wrong place. Thirty milliseconds is invisible against a cell that takes half
a second and is fifteen times the cost of a cell that filters a small frame. The
commit therefore happens **off the execution path**: the result returns to the
interface, and the commit is queued behind it. The queued commit records the
notebook as captured at execution time rather than as read from disk, so a
second cell run during the interval cannot corrupt the first commit's content.

Volume is a genuine constraint, and it lands on history rather than on disk. A
thousand commits a day accumulate on a branch that, under the branching model
in ARCHITECTURE.md §4.6, represents one data context — one batch, one
instrument, one cohort — and carries that context's workflow history. Burying
that history under machine-generated commits would take away the reason branches
are useful here.

Explore commits are therefore written to a **dedicated ref namespace** rather
than to the branch. The fine-grained history stays addressable, lineage records
reference its shas, and `git log` on the branch continues to describe what a
person did. A session writes a single meaningful commit onto the branch when the
user asks for one or when the session ends.

Because the project ships its own git, packing must be ensured rather than
assumed; git's default auto-gc threshold of 6700 loose objects corresponds to
roughly a week of heavy use.

### 7.1 A Session Belongs To The Branch It Was Opened On

ARCHITECTURE.md §4.6 describes how branches are used here: one branch carries
one data context — a batch, an instrument, a cohort — along with the workflow
variant adapted to it, and merging is usually beside the point. An Explore
Session is a file on such a branch and travels with it, so the exploration of
one batch sits beside the workflow that batch is analysed with.

Adapting an exploration to a new data context therefore uses the mechanism the
project already has for adapting a workflow: branch, point the first cell at the
new context's reference, and re-run. The self-contained first cell of §2 is what
makes the rest of the notebook carry over untouched.

Switching branches while a session is open **retires the kernel**. The kernel
holds one context's data, and the branch switch means the user is now working on
another; carrying the objects across would produce a session whose memory and
whose files disagree. Retirement is inexpensive because the notebook replays.
This is stated explicitly because branch switching under live application state
has already produced defects in this product (#1872), and a resident kernel is
more state than a canvas.

A branch may hold **several sessions**, since one data context can reasonably be
explored from more than one angle at once, and coexisting files avoid making the
user switch working trees to change the question they are asking.

Carrying an improvement from one data context to the others is a **subgraph
operation** and not a text merge. The user selects a connected region of the
dependency graph, and its inputs are rebound to the corresponding versions in
the target session. This is what the graph view of §2.1 exists to make
selectable, and it is why §14.4's diff-legibility argument does not decide the
storage format.

## 8. Explore Lineage Anchors On A Session

Lineage today is four tables: `runs`, `block_executions`, `data_objects`, and
`block_io`, with object identity carried in a `DataObject`'s framework metadata
(`core/lineage/record.py`). Exploration needs the same downstream structure and
a different anchor, because there is no workflow and no run.

One table is added. `explore_sessions` parallels `runs` field for field: where
a `RunRecord` carries `workflow_id`, `workflow_yaml_snapshot`, and
`workflow_git_commit`, an explore session carries the notebook's path, its
captured content, and the commit written in §7. Both carry an environment
snapshot, a start time, and a status.

The other three tables are used unchanged. A block call from a cell writes an
ordinary `BlockExecutionRecord` — `block_id`, `block_type`, `block_version`,
`block_config_resolved` are the fields it already has — with its foreign key
pointing at a session instead of a run. Objects and their input/output edges go
into `data_objects` and `block_io` as they always have.

Independence therefore stops at the anchor, and the chain across the boundary
stays intact through `object_id`. A reference produced during exploration and
later consumed by a workflow appears as that run's input, and the explore side
records where it came from. Following provenance across the boundary requires no
bridging code, because content identity is already the shared key.

Provenance is consequently **graded**, and the grade follows §6. A block-call
cell records what a workflow node records, and promotion carries that record
across unchanged. A free-form cell records the session, the notebook commit, the
cell, and the environment — enough to replay, and not enough to describe.
Replaying is well defined because the notebook loads its own input in cell one
and executes in written order.

Records are written per cell run, which costs **0.07 ms and 212 bytes** on the
existing SQLite store in WAL mode. At a thousand cell runs a day this is 70 ms
and 212 KB, so the recording rate needs no rationing. The environment snapshot
is the one field that must not be inlined per record: `EnvironmentSnapshot`
carries an optional full `pip freeze`, and duplicating it into every cell run
would turn a 212-byte row into a five-figure one. It is stored once per distinct
environment and referenced.

Retention reuses a decision the session already makes. Exploration produces many
intermediate objects and abandons most of them; the objects a user has declared
as session outputs (§9) are durable, and the remainder are reclaim candidates
for the existing planner in `core/lineage/retention.py`. No new user-facing
concept is introduced to express this.

## 9. Promotion Produces A Code Block

An Explore Session declares outputs the way a block declares them: the user
marks variables as outputs during exploration, and those variables are collected
into typed output collections when the session is promoted.

The resulting correspondence is exact. The reference the session was created
from is its input port; the marked variables are its output ports; the notebook
is its implementation. Promotion packages the three into a Code Block, and the
Code Block notebook backend already executes `.ipynb` as a workflow step
(`blocks/code/backends/notebook.py`).

The work promotion has to do is bounded by §6. Cells that call blocks map onto
workflow nodes directly, carrying their recorded parameters and versions. Cells
of free-form code are packaged as the block's script. The dependency graph of
§5 supplies the edges.

A promoted session can contain **parallel branches**, because comparing two
thresholds side by side is the ordinary way exploration proceeds and each
alternative becomes its own chain of variable versions. The workflow canvas must
render a graph with divergent branches correctly, which is stated here as a
requirement on promotion rather than left to be discovered when the first
branched session is promoted.

Objects written back are **new references**. Overwriting the reference the
session was opened from would change the input of workflow nodes that have
already executed against it, breaking lineage that was correct when it was
recorded.

## 10. Existing Panels Are Refactored Before New Ones Are Built

The migration order is to bring the panels that exist onto the contract in §3
first, retaining compatibility, and to build the Explore Session on the contract
afterwards.

The order is chosen so that the contract meets real panels before it acquires
dependents. Between them, previewers and interactive-block panels already
exercise both discovery mechanisms, the loading path, the version gate, and the
failure behaviour, none of which are specific to exploration. A contract that
has already carried the imaging previewer and the interactive-block modal is a
contract the Explore Session can build on; a contract designed against
exploration alone would meet those cases afterwards, when changing it is
expensive.

The convergence noted in §6 is the concrete payoff: once an interactive block's
panel is a framed HTML document under the unified contract, it serves as a modal
during a workflow run and as the session's panel during exploration with no
second implementation.

Moving previewers from the ADR-048 ES-module contract to the unified one is a
breaking change to a contract that packages already implement, and it requires
an addendum to ADR-048 and a migration for `scistudio-blocks-imaging`. Doing it
now is materially cheaper than doing it after more packages ship panel assets.
The asset whitelist in `previewers/assets.py` gains the file types the unified
contract serves, and the two API versions become one.

## 11. Scope

In scope: the Explore Session as a tab, its notebook and resident kernel, the
unified panel contract and its migration, in-kernel block execution, per-cell-run
commits on a dedicated ref, the `explore_sessions` lineage anchor, and promotion
to a Code Block.

Out of scope: replacing the workflow editing mode; a general-purpose notebook
IDE; modification of existing artifacts in place; automatic merging of Explore
branches; importing external `.ipynb` files, which §5's analysis would need to
report on rather than assume.

Delivery is staged. A first slice covers one data type, a small set of panel
edits, the resident kernel, panel-to-code generation, and promotion, which is
enough to test whether the loop is worth using before array and image panels,
reverse synchronisation, and the graph view are built.

## 12. Verification And Tooling Impact

This ADR is in planning phase and governs no implementation yet; the surfaces in
`planned_governs` become governed as they land.

Verification expectations by area. The dependency analysis needs unit coverage
over the binding forms it must recognise and over the in-place cases it must
report. The unified panel contract needs the loader tests the two existing
loaders already carry, run against one implementation. Kernel lifecycle needs
coverage of restart, interrupt during a hung cell, and environment re-snapshot
after an install. Lineage needs coverage that an object produced in a session
and consumed by a workflow run resolves across the boundary. Promotion needs
coverage that a session containing both step kinds produces a Code Block that
executes, including one with parallel branches.

The commit and lineage measurements in §7 and §8 were taken on the paths this
ADR relies on and should be re-taken if `GitEngine`'s invocation pattern or the
lineage store's durability settings change.

## 13. Consequences And Risks

Exploration will surface missing dependencies far more often than workflow
execution does, and the bundled runtime cannot receive them through OTA. The
`%pip` path in §4 is the mitigation, and its adequacy is the single most likely
early blocker on this feature being usable.

In-kernel block execution means a block that crashes the interpreter ends the
session. Recovery is a restart and a replay, which is acceptable, and which
depends on the replay property holding — so anything that weakens the
self-contained first cell weakens crash recovery too.

In-place mutation escapes the dependency graph. Panels do not produce it and
users can, so a session containing hand-written in-place mutation may show a
stale panel. Reporting it is the available answer.

Retaining Explore branches without merging them means a project accumulates
them. This follows ARCHITECTURE.md §4.6, where branches carry parallel analysis
variants and merging is not the goal, so the accumulation is expected rather
than a defect; retention of the objects they produced is governed by §8.

Migrating previewers breaks a shipped contract. The cost is a package migration
now against a larger one later.

## 14. Alternatives Considered

### 14.1 AnyWidget Modules Instead Of Framed HTML Documents

Authoring panels as AnyWidget modules — an ES module exporting
`render({ model, el })` against a Python object whose traits synchronise with
the front end — would let a notebook's panels render in JupyterLab, VS Code, and
Colab, matching the portability motive behind storing notebooks as `.ipynb`.

It was rejected on two grounds. The portability it buys is narrower than it
appears: a notebook taken elsewhere already executes all of its code and
describes its own inputs, so what travelling panels would add is SciStudio's own
interactive surface in someone else's tool, which is not what a user carrying a
notebook out is asking for.

The second ground is decisive given who writes these panels. Against a
self-contained HTML document, an AnyWidget module is harder for an agent to
author well: it cannot be rendered and inspected without a running kernel, its
trait and event vocabulary is represented in far less public material than plain
HTML, and a mistake in it executes in the application's own realm rather than in
a frame that can be discarded. Choosing the format that an agent can test and
fail at safely follows the same reasoning ADR-053 §4 applies to blocks.

Trait synchronisation was also the one place where this ADR's central guarantee
would have needed policing, since a panel could have written data through a
trait and left no code behind. Removing the channel removes the rule.

### 14.2 Name-Keyed Reactive Semantics

Deriving the dependency graph from global variable names is the established
approach and removes the ordering requirement in §5. It forbids defining a
variable twice, which the target users do constantly. Adopting it would have
required teaching Jupyter-fluent scientists to write differently in exchange for
a property they can get without changing anything.

### 14.3 Executing Blocks Through The Workflow Runner

Submitting a notebook block call to the real engine would produce artifacts and
lineage identical to a workflow run and would isolate the block in a subprocess.
It was rejected on latency: a subprocess launch and an artifact round trip per
call is the wrong cost for a surface built for iteration. The provenance
difference is smaller than it appears, because §8 records the same
`BlockExecutionRecord` either way.

### 14.4 Storing Notebooks As Text

A percent-format `.py` produces readable diffs and straightforward text merges,
and the JSON structure of `.ipynb` produces neither. The reasons for `.ipynb`
are given in §7; what remains is whether the diff argument should have
outweighed them, and it should not. Propagating an improvement between data
contexts operates on the dependency graph of §5 — a connected subgraph, its
inputs rebound — so the mechanism that would have depended on legible text does
not use text at all. Stripping outputs removes most of the remaining noise.

### 14.5 One Notebook Per Branch

Restricting a branch to a single Explore Session would simplify session
lifecycle. It conflicts with how the branching model is used: a branch is one
data context, and a user may reasonably explore that context from several angles
at once. Multiple sessions coexist as files on a branch.

### 14.6 Rendering The Workflow Linearly Instead Of Creating A File

If an Explore Session were another view of the workflow it came from, promotion
would disappear. It would also force every exploratory statement to be a
declared node with typed ports, which reintroduces the up-front declaration cost
this ADR exists to remove.
