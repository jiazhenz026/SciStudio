# ADR-054: Panels: User-Customizable HTML Pages For Previewing And Deciding On Data

## 1. Decision Summary

A scientist spends much of a working day looking at data inside SciStudio: a
table a block produced, an image stack, a spectrum. Now and then a workflow
stops and asks them to decide something about that data — which run is the
blank, which objects are real — before it can continue. Both moments are the
same act. A page shows some data, and sometimes it lets a person answer a
question about it. What a good page looks like depends on the data and on the
person: a spectroscopy group wants peaks labelled the way it labels them, an
imaging group wants its own overlay. The person best placed to ask for that page
is the scientist, and in practice the one writing it is the agent working on
their behalf.

SciStudio has two separate systems for these moments. ADR-048 previewers show
data and change nothing; ADR-051 interactive blocks open a window that returns a
decision. Each can load a package's own frontend module, but through its own
loader, its own host API, and its own asset route, and in both the module runs
inside the application's own page with the application's full privileges. The
built-in viewers a scientist uses most are compiled into the frontend and cannot
be changed at all.

This ADR introduces **panels**. A panel is a user-customizable HTML page whose
job is to show a page about some data. It does exactly three things: it reads
the data it needs, it writes the user's answer back, and — in a notebook context
that a separate ADR will define — it keeps one kernel variable in sync. Every
surface for previewing data or deciding on it becomes a panel, the built-in ones
included.

The design follows from that description. A panel does three things, and what it
is allowed to do is decided by the context that opened it rather than by the
panel (Section 2). A panel is a folder that says which contexts it was written
for, installed at the same tiers as today's previewers (Section 3). The page
runs in a sandbox and speaks only to its host, so a faulty page cannot reach the
application (Section 4). Reading data needs no code of the panel's own, because
everything inside SciStudio's canonical zone can be read through a small set of
bounded reads (Section 5). The built-in viewers become ordinary panels, and every
panel draws its libraries from a known shelf (Section 6). The parts of ADR-048
and ADR-051 that are not about the page stay exactly as they are (Section 7). The
old module contract keeps working, deprecated, through the 0.5 line (Section 8).
Richer writing back and notebook sync grow by adding contexts rather than by
changing panels (Section 9).

This ADR keeps ADR-048's routing ladder, its read-only rule, and its bounded
data-access contract, and replaces its frontend module contract. It keeps
ADR-051's interaction capability, its two-phase subprocess runtime, and ADR-051
Addendum 1, and replaces its window contract. ADR-052 governs the public surface
that changes and the one that appears; ADR-049 gains the panel checks; ADR-055's
desktop, browser, and Lab deployments all host panels the same way. Section 5
rests on the canonical-zone model of ADR-041 and ADR-043.

### 1.1 Problems Addressed

| Problem | Risk | ADR response | Detailed section |

## 2. A Panel Shows Data And Does Three Things

The two systems look different, but a person using either is doing the same
thing: looking at a page about some data and, sometimes, telling SciStudio what
they concluded. Seen that way, a panel never needs more than three operations.

| Operation | What it means |
|---|---|
| **read** | Get the data the page needs, in bounded windows — a page of rows, a plane, a tile |
| **write back** | Hand the user's answer to whoever opened the panel |
| **sync** | Receive changes pushed from the data's owner and push edits back to it (reserved; Section 9) |

A panel does not know where it is. The thing that opened it — its **context** —
decides what the panel is given and which of the three operations exist.

| Context | What the panel is given | read | write back | sync |
|---|---|---|---|---|
| `preview` | A reference to one typed data object: its type, metadata, and shape. Contents are read on demand | yes | no | no |
| `interactive` | The JSON view built by the block's `prepare_prompt` (ADR-051 §2), and the block's inputs by reference | yes | once — the decision | no |
| notebook (separate ADR) | A kernel variable | yes | yes | yes |

This table is the whole permission model. An operation a context does not
provide is not there for the panel to call, so a previewer is read-only because
the preview context offers no write back, not because a page promises to behave.
A panel declares nothing about what it may do, and the tier it was installed
from does not change what it may do.

Declaring permissions in the panel was considered and rejected. It would create
a public permission vocabulary that has to be documented, validated by ADR-049,
and kept compatible as it grows, to say something the context already knows.
Granting less to panels installed at the project tier was rejected for a related
reason: opening a project already imports that project's Python previewer
drop-ins into the backend process with full privileges
(`src/scistudio/previewers/session.py`), so a sandboxed HTML page is the smaller
risk, not the one that needs a separate trust rule.

Writing back never makes the frontend the record of truth. In the interactive
context the answer travels the existing ADR-051 path — the host sends it to the
backend, the engine resumes the block, and the decision is recorded in lineage
through `block_config_resolved` — so the panel's part ends when it hands the
answer over.

## 3. A Panel Is A Folder That Says Where It Belongs

A panel is a directory: a short manifest, the page, and any static files the page
loads.

```text
<tier root>/panels/<panel-id>/
  panel.json      # id, display name, contexts, types
  index.html      # the page
  ...             # images, styles, scripts the page references
```

The manifest has one field that matters to this ADR, `contexts`, which lists the
contexts the panel was written for.

```json
{ "id": "imaging.image", "contexts": ["preview"], "types": ["Image"] }

{ "id": "lcms.background_subtraction", "contexts": ["interactive"] }

{ "id": "qc.review", "contexts": ["preview", "interactive"], "types": ["Image"] }
```

The field exists because the two contexts hand a panel different things. A page
written to preview an `Image` expects a typed data object; a block hands its
panel whatever JSON its own `prepare_prompt` built. A preview page opened by a
block would not understand what it was given and would never write back, and
the block would sit paused until the scientist cancelled it. Declaring the
contexts turns that silent hang into a load-time error. This is a statement of
compatibility — where the panel can be used — and it is separate from the
permission model of Section 2, which still decides what the panel can do there.

The rules are few. `contexts` names at least one known context. When it includes
`preview`, `types` is required, and `types` is exactly the information the
previewer routing ladder needs, so there is no separate previewer declaration to
keep in step with the panel. A block whose `interactive_panel` names a panel that
does not declare `interactive` is refused when the block is discovered, the same
way ADR-051 already refuses a block whose capability and execution mode
disagree, and the ADR-049 package validator reports the same mismatch before a
package ships. This ADR accepts `preview` and `interactive`; the notebook ADR
adds its own value, and adding a value leaves existing panels untouched.

Panels install at the four tiers previewers already use — core, installed
packages, the user library of ADR-053, and the open project — and registration is
the directory itself, so a person or the agent adds a panel by writing files. A
preview panel is chosen by the ADR-048 §3 ladder over its `types`: project over
user over package over core, exact types before parent types, an explicit
ambiguity error on an unresolved tie, and the per-type user choice
(`src/scistudio/previewers/choices.py`) above all of it. An interactive panel is
chosen by name, because the block that opens it names it.

## 4. The Page Runs In A Sandbox And Speaks Only To Its Host

A panel is mounted in an `iframe` with `sandbox="allow-scripts"` and without
`allow-same-origin`. The browser then gives the page an opaque origin of its
own. The page can run its script, but it cannot read the application's document,
storage, or cookies, and it cannot call the backend API. The only thing it can do
is exchange messages with the host that mounted it.

This is what makes the permission model of Section 2 real. Today a previewer
module is read-only only because its host API offers no write method
(`frontend/src/components/DataPreview.parts/previewerHostApi.ts`); the module runs
in the application's own context, so nothing stops it calling any `/api` route.
Inside the frame, the operations the host provides are the only reach the panel
has. The same boundary contains mistakes: a thrown exception, a leaked global
handler, or a page that renders itself into a stall stays inside a frame the host
can discard and remount. Panels are written mostly by agents, and an agent's
first attempt has to be able to fail without consequence.

The host implements the operations over the backend it is already connected to.
A small SDK inside the page turns each operation into a message, and the host
answers it:

- `read` with a query — which rows, which plane, which tile — answered by the
  core read layer of Section 5, with binary data transferred as `ArrayBuffer`
  rather than copied;
- `write back` with a JSON value, present only where the context provides it;
- `sync`, reserved for the notebook context;
- housekeeping: signalling readiness, receiving theme tokens and size changes,
  and asking the host to save a file through its native dialog, as the preview
  system's save-resource flow does today.

The message schema, the exact shape of each read, and the library the SDK ships
as are specification detail. Because everything passes through the host, panels
behave identically in the desktop window, which already runs with
`sandbox: true` and `contextIsolation: true` (`desktop/main.js`), in an ordinary
browser, and behind JupyterHub's path-based routing in the Lab deployment of
ADR-055 §8. No deployment needs a second address.

Three other placements of the page were weighed. A same-origin frame that is
also allowed to run scripts can reach the host document and remove its own
sandbox attribute, so it isolates nothing; it is today's arrangement drawn inside
a rectangle. A page served from a separate origin is isolated and could fetch
data directly, but every deployment would need a second address, the Lab
deployment would have to bring that address under the Hub authentication ADR-055
§8 requires for every endpoint, and the backend would need a scoped-token
authorization layer to decide per context what each page may call. Forwarding
arbitrary HTTP requests from the page through the host, checked against a
per-context whitelist of routes, was the closest alternative. It was rejected
because it turns every forwarded backend route into a contract panel authors
depend on and ADR-052 must keep stable, and it maintains a whitelist to express
what three operations already say.

The frame boundary has costs the specification must handle. Menus and tooltips
cannot draw outside the panel's rectangle; the host's keyboard shortcuts do not
fire while the page has focus; clipboard and fullscreen access need explicit
frame permissions; downloads go through the host; and the page cannot see the
application's CSS or fonts, so the host passes theme tokens (#1849). Because the
page's origin is opaque, the asset route answers its module scripts and fetches
as cross-origin requests, and the path-confined asset allowlist
(`src/scistudio/previewers/assets.py`) gains `.html`.

## 5. Reading Data Needs No Code Of The Panel's Own

Everything a panel can be asked to show already lives inside SciStudio's
**canonical zone** (ARCHITECTURE.md §4.3.2). Once data has entered a workflow it
is a typed data object with a storage reference; arrays are stored in Zarr,
tables in Arrow or Parquet, and anything else as a file artifact kept as it is.
Types do not own file formats, and format conversion happens only at IO
boundaries (ADR-043 §1). A small set of bounded reads therefore covers every
type: pages of a table, planes and tiles of an array, decimated series, chunks of
text, the slots of composite data, and the items of a collection. ADR-048 §7
already defines those reads and `PreviewDataAccess` implements them. That layer
answers a panel's `read`.

The panel receives values, not pictures, and does its own shaping in JavaScript.
This is usually better than today's arrangement, not merely equivalent. The
imaging previewer's backend sends its page a plane downsampled to at most 256
pixels on a side (`PreviewLimits.max_dim`), and the page's contrast control
remaps the pixels of a grayscale PNG the backend encoded from it
(`applyLUTToImage` in the package's `viewer.js`). A panel that reads the plane's
actual values, window by window, can adjust contrast across the full dynamic
range at the resolution it is showing, without asking the backend again.

A panel therefore has no Python of its own. Today a previewer pairs its frontend
module with a Python provider, and the reason was that the page could not be
customized, so the shaping had to happen on the backend. The providers in the
existing packages bear this out. The spectroscopy provider reads through
`PreviewDataAccess` and pages, filters, groups, and checks the integrity of
bounded rows; its own contract states that those checks perform no scientific
processing. The imaging provider
reads through the same layer and adds downsampling and PNG encoding. Its
TIFF and Pillow decoder is a fallback moved out of core by the hotfix for #1703,
and no code path found produces the non-Zarr image references it serves. All of
that work can happen in the page.

The one need a page cannot meet by itself is a computation over a whole large
dataset — a histogram of an entire image for automatic contrast, a statistic over
millions of rows — because it only ever sees windows. The providers have the same
limit today: they compute over bounded reads and report partial results. When
such reads are needed, they belong in the core read layer as generic reads, not
in per-panel code. The other contexts already have their Python side: an
interactive block's `prepare_prompt` builds its view, and a notebook's kernel
owns its variables.

An optional per-panel provider was considered and rejected. It would bring a
Python execution venue that must stay off the API event loop (ADR-048 §8),
a lifecycle, a place in the SDK, and project-tier Python code to trust, in order
to preserve work the page can do. Routing a panel's calls to a different Python
side per context — provider, `prepare_prompt`, kernel — was rejected with it,
because it was the source of most of the model's accidental complexity.

## 6. Built-In Panels Are Ordinary Panels

The viewers SciStudio ships are rewritten as panels and installed at the core
tier: the nine core previewers registered in `src/scistudio/previewers/fallbacks.py`
(`core.dataframe.basic`, `core.array.basic`, `core.series.basic`,
`core.text.basic`, `core.artifact.basic`, `core.composite.basic`,
`core.collection.basic`, `core.plot.basic`, and `core.base.fallback`) and the two
built-in interactive windows, `DataRouterModal` and `PairEditorModal`. They are
served by the same route, mounted in the same sandbox, and given the same three
operations as every other panel. They have no privilege a package panel lacks,
and a user or project panel with the same id shadows one. The frontend keeps no
mapping from a preview kind to a compiled component.

Keeping the built-ins as compiled React components was rejected. It would leave
two rendering paths in the application indefinitely, and it would leave the
views people use most as the only ones they cannot adjust.

Panels need libraries — plotting, tables, 3-D rendering — and the frame cannot
use the ones the application has already loaded. SciStudio ships a local set of
common libraries at fixed URLs that carry their version. Built-in panels use only
that set, so they work without a network connection. Custom panels are expected
to prefer it, and the agent's context tells authors so, but they may also
reference a public CDN. A CDN is fetched by the user's browser, which in the Lab
deployment is the scientist's own computer (ADR-055 §2), so a CDN reference fails
only when that browser is offline or blocked. Relying on a CDN alone was rejected
because built-in panels would go blank offline; requiring every panel to bundle
its own copies was rejected because it duplicates libraries and makes every
author, including the agent, carry them. The versioned URLs make the local set a
contract: how long superseded versions stay available is specification detail.

## 7. What Stays As It Is

Previewers remain read-only. ADR-048 §4 says a previewer must not mutate workflow
definitions, runtime state, lineage, or project files, and under this ADR the
preview context provides no write back at all.

ADR-051 §3 is unchanged. An interactive block still runs in two subprocesses on
either side of the pause, with nothing resident while the person decides, and the
interaction is still a single round. `prepare_prompt` runs once when the window
opens; while the block is paused the panel reads only through the core read
layer, which runs no block code. ADR-051 Addendum 1's interaction memory is
unchanged, and the interactive window is still the full-screen modal the
application draws today.

ADR-048's routing ladder, its ambiguity rule, the per-type user choice, and the
path confinement of the asset route all carry over to panels as they are.

## 8. The Old Contract Has An End Date

The current contract is an ES module that exports `mount(container, host)` and is
imported into the application's own page — through `FrontendManifest` and
`frontend/src/components/DataPreview.parts/dynamicPreviewer.ts` for previewers,
and through ADR-051's `PanelManifest` and
`frontend/src/App.parts/InteractiveModals.parts/panelModuleLoader.ts` for
interactive blocks. It has real users: the imaging and spectroscopy packages each
ship two previewers with their own frontend module, the LCMS package ships four
interactive panels, and the core tutorial "What Is A Type" teaches readers to
write both a previewer and a panel module in this form.

Every public symbol involved is `provisional` (ADR-052 §5), so a minor release
could change it with a changelog entry. The owner chose a transition instead. The
old contract stays supported and deprecated, with a runtime warning, through the
0.5 line, and is removed in 0.6; the current version is 0.3.4. Its removal is
tracked from #2285. Until then a legacy module still runs in the application's
own page, so the isolation of Section 4 is complete only once the old contract is
gone. The compatibility path gains no feature of the new model — no contexts, no
operations — because a shim that grows the new surface becomes a second
implementation that never leaves.

## 9. Writing Back And Syncing Grow By Adding Contexts

Editing data from a preview, and the notebook, are outside this ADR, and the
model is shaped so that neither needs a panel to change. Letting a person edit
data means adding a context that provides write back with a defined meaning —
what is written, how a new version is recorded in lineage — and the panel, its
SDK, and its sandbox stay as they are. The notebook ADR defines the notebook
context, the semantics of `sync`, and the `notebook` value of `contexts`. This ADR
only guarantees that nothing in it stands in their way. Both are tracked from
#2285.

## 10. Scope

In scope: the panel concept and its three operations; the context model and the
table of Section 2 as the permission model; `panel.json` with `contexts` and
`types` and the load-time and validator checks of Section 3; the sandboxed frame
and host-mediated SDK of Section 4; the core read layer as the only data path of
Section 5; rewriting the built-in viewers and interactive windows as core-tier
panels and shipping the local library set of Section 6; and the deprecation and
removal schedule of Section 8.

Out of scope, each tracked from #2285: editing data from a preview or any other
context beyond an interactive block's decision; the notebook context and `sync`;
per-panel Python providers; editing a panel's source inside the application
rather than as files on disk; and any change to the ADR-051 §3 runtime.

## 12. Verification And Tooling Impact

This ADR is documentation-only; implementation and its tests land in the
implementation PRs tracked from #2285.

The decision is verified where each guarantee lives. The sandbox is verified by
confirming that every panel mounts in a frame without `allow-same-origin` and that
a page's direct attempt to call the backend fails. The permission model is
verified by confirming that a preview panel has no write back and an interactive
panel can write back exactly once. The manifest rules are verified by confirming
that an empty or unknown `contexts`, a `preview` panel without `types`, and a
block naming a panel without `interactive` are each refused, at load time and by
the ADR-049 validator. The built-ins are verified by confirming they resolve
through the same route and ladder as package panels and render with no network
access. The transition is verified by confirming that legacy modules still load,
with a deprecation warning, until the release that removes them. The existing
tests listed in the frontmatter change with the implementation.

## 13. Consequences And Risks

SciStudio gains one mechanism where it had two. A panel is one HTML page and a
short manifest, which is the form an agent writes most reliably and can check by
opening the page with sample data. Built-in viewers become adjustable, a faulty
page can no longer reach the application, and the same panel runs in every
deployment.

The cost is concentrated in migration. Every built-in viewer and both built-in
interactive windows are rewritten. The imaging and spectroscopy packages move
their frontends into panels and port their provider shaping — about 1,570 lines
of Python across the two — to JavaScript; the LCMS package moves four panels. The
tutorial that teaches the old contract is rewritten. Two loaders coexist until
0.6, and legacy modules stay unsandboxed until then.

The frame boundary costs some polish, listed in Section 4, and reads that used to
be a function call inside the page become a message round trip, which windowed
reads and transferred buffers keep small. The local library set becomes a
versioned contract that must be maintained, patched, and licensed. A custom panel
that relies on a CDN fails when its user is offline. The public surface also
changes: the provisional manifest types are retired on the schedule of Section 8,
and `panel.json` and the SDK become the new author-facing surface under ADR-052.

## 14. Alternatives Considered

**A same-origin frame.** Rejected because a frame allowed both scripts and its
host's origin can remove its own sandbox, so it isolates nothing.

**A separate origin for panels.** Rejected because every deployment would need a
second address brought under its authentication, and the backend would need a
per-context token authorization layer.

**Forwarding arbitrary HTTP requests through the host against a route
whitelist.** Rejected because forwarded routes become a stable contract and the
whitelist restates what three operations express directly.

**Permissions declared by the panel, or granted by install tier.** Rejected
because the context already knows what a panel may do, and a permission
vocabulary is a second contract to maintain.

**An optional Python provider per panel, or per-context routing of a panel's
Python calls.** Rejected because canonical storage makes bounded reads sufficient
and every other context already has its Python side.

**Keeping built-in viewers as compiled React components.** Rejected because it
keeps two rendering paths and leaves the most-used views unadjustable.

**CDN-only libraries, or libraries bundled by every panel.** Rejected because the
first breaks built-in panels offline and the second duplicates libraries in every
panel.

**Declaring the `notebook` context now.** Rejected because a context value that
nothing can yet open is untestable; the notebook ADR adds it.

**Removing the old contract immediately.** Rejected because installed packages
and a core tutorial depend on it; it ends in 0.6 instead.
