# ADR-054: Panels: User-Customizable HTML Pages For Previewing, Deciding On, And Exploring Data

## 1. Decision Summary

A scientist spends much of a working day looking at data inside SciStudio: a
table a block produced, a set of images, a spectrum. Now and then a workflow
stops and asks them to decide something about that data — which run is the
blank, which objects are real — before it can continue. Both moments are the
same act. A page shows some data, and sometimes it lets a person answer a
question about it. What a good page looks like depends on the data and on the
person: a spectroscopy group wants peaks labelled the way it labels them, an
imaging group wants its own overlay. The person best placed to ask for that page
is the scientist, and in practice the one writing it is the agent working on
their behalf.

There is a third moment that neither reaches. Often a scientist cannot know what
the next step of an analysis should be until they have seen the result of the
last one, and what they need in order to see it is not a fixed view but a small
tool of their own: a threshold they can drag across an image stack and watch the
segmentation follow, two runs' peak tables laid side by side. An agent can write
such a tool in minutes. Most scientists do not know that it can, and SciStudio has
no place for the tool to live.

SciStudio has two separate systems for these moments. ADR-048 previewers show
data and change nothing; ADR-051 interactive blocks open a window that returns a
decision. Each can load a package's own frontend module, but through its own
loader, its own host API, and its own asset route, and in both the module runs
inside the application's own page with the application's full privileges. The
built-in viewers a scientist uses most are compiled into the frontend and cannot
be changed at all.

This ADR introduces **panels**. A panel is a user-customizable HTML page whose
job is to show a page about some data. Its page does no more than four things:
it reads the data it needs, it writes the user's answer back, it calls the
panel's own Python, and — in a notebook context a later ADR may define — it keeps
one kernel variable in sync. Which of these a panel may do is decided by the
context that opened it. Every surface for previewing data or deciding on it
becomes a panel, the built-in ones included, and a new context turns a panel into
a **MiniApp**: a small exploration app the agent writes for the user on request,
with a page and a Python process of its own.

The design follows from that description. What a panel may do and read is
decided by the context that opened it rather than by the panel (Section 2). A
panel is a folder that says which contexts it was written for and how it competes
for a data type (Section 3). The page runs in a sandbox,
reaches the backend only through its host, and loads its own files under the
same login as the rest of SciStudio (Section 4). Reading data needs no code of
the panel's own, because the canonical zone can be read through a small set of
bounded reads, which this ADR extends where they fall short (Section 5). The
built-in viewers become ordinary panels, and every panel draws its libraries from
a known shelf (Section 6). The parts of ADR-048 and ADR-051 that are not about
the page stay as they are (Section 7). Both kinds of existing previewer keep
working, deprecated, through the 0.5 line (Section 8). Richer writing back and
notebook sync grow by adding contexts (Section 9). A panel may carry its own
Python, which runs only where the context provides the operation that calls it
(Section 10), and the `miniapp` context is the first that does: what a MiniApp is,
how a user finds and makes one, and how an exploration becomes a workflow step
(Section 11).

This ADR keeps ADR-048's routing ladder, its read-only rule, and its bounded
data-access contract, and replaces its frontend module contract, including its
rule that frontend code loads only from the SciStudio origin (Section 6). It keeps
ADR-051 and ADR-051 Addendum 1 unchanged apart from the window contract. ADR-052
governs the public surface that changes and the one that appears; ADR-049 gains
panel checks and changes one blocking check; ADR-055's desktop, browser, and Lab
deployments all host panels the same way, with one documented authentication
exception (Section 4). Section 5 rests on the canonical-zone model of ADR-041
and ADR-043. MiniApps reuse the application's process registry, where the
commands the agent runs are registered (ADR-055 §5.3), the process-tree handling
of block processes (ADR-017), the guided agent session and the promotion to the
user library of ADR-053, and the agent's provisioned skills and tools (ADR-040); ADR-051 is unchanged, and an
interactive panel never runs Python. The text was revised after a no-context
audit (`docs/audit/2026-09-11-adr-054-panels-no-context.md`) and extended with
MiniApps in #2341.

## 2. A Panel Shows Data, And Its Context Decides What It May Do

The two systems look different, but a person using either is doing the same
thing: looking at a page about some data and, sometimes, telling SciStudio what
they concluded. Seen that way, a panel needs only a few operations.

| Operation | What it means |
|---|---|
| **read** | Get the data the page needs — handed over when the panel opens, or read in bounded windows such as a page of rows or a tile |
| **write back** | Hand the user's answer to whoever opened the panel |
| **call** | Ask the panel's own Python, `panel.py`, to compute something and return the result (Section 10) |
| **sync** | Receive changes pushed from the data's owner and push edits back to it (reserved; Section 9) |

A panel does not know where it is. The thing that opened it — its **context** —
decides what the panel is given, what it may read, and which operations exist.

| Context | What the panel is given | What it may read | write back | call | sync |
|---|---|---|---|---|---|
| `preview` | A reference to the previewed target: one typed data object, or a collection given as its item count, item type, and a page of item references | The target and, for composite data and collections, its slots and items | no | no | no |
| `interactive` | The JSON view the block's `prepare_prompt` built (ADR-051 §2) | Nothing beyond that view | once — the decision | no | no |
| `miniapp` | A reference to the data the user chose to open the MiniApp on, of the type it declares | That data and, for composite data and collections, its slots and items | no | yes | no |
| notebook (a later ADR) | A kernel variable | That variable | yes | not defined | yes |

This table is the whole permission model. An operation a context does not
provide is not there for the panel to call, and a read outside what the context
authorizes is refused by the backend, not only by the host. A previewer is
read-only because the preview context offers no write back, not because a page
promises to behave. A panel declares nothing about what it may do, and the tier
it was installed from does not change it.

The table governs the page. A panel's Python is different in kind: where a
context starts it, it runs as the user, with the reach of a Code Block or of a
command the agent runs (ADR-055 §5.3), and no content policy confines it. That is
why whether it runs is decided here, by the context, and never by the panel. The
`preview` and `interactive` contexts do not start it, which keeps a previewer
read-only in fact and an interactive window self-contained as ADR-051 §4
requires; the `miniapp` context does, and a MiniApp is therefore not read-only
(Section 10).

The interactive row is deliberately narrow. ADR-051 §2 makes reducing the data to
a window-sized view the block's job, because only the block knows which reduction
is meaningful, and ADR-051 §4 makes the window self-contained so the engine can
hold the pause with nothing resident. An interactive panel therefore receives the
block's view and nothing else. Letting it read the block's inputs by reference
during the pause was considered and rejected: it would amend ADR-051 §2 through
§4, add input references to the pause event, and send data to the browser that
the block chose not to send.

Besides the operations, the host offers two services that move nothing
into the backend's data. **Open** asks the host to show a child of the previewed
target — an item of a collection, a slot of composite data — in the panel the
routing ladder picks for the child's type, keeping the drill-down stack and its
back action exactly as the preview host keeps them today
(`frontend/src/components/DataPreview.parts/PreviewHost.tsx`). It exists only in
the preview context and only for children of the target. The backend authorizes
that child and routes it through the shared panel/legacy preview pipeline. Its
preview session retains independent frozen source authority across parent-context
close and maximize, with source validity checked on subsequent session reads.
**Save** hands the host
bytes the page produced, such as an exported figure, and the host writes them
where the user chooses in a native dialog or a browser download, under a size
limit; it never writes into the project without that choice.

Declaring permissions in the panel was considered and rejected. It would create a
public permission vocabulary that has to be documented, validated by ADR-049, and
kept compatible as it grows, to say something the context already knows. Granting
less to panels installed at the project tier was rejected for a related reason:
the controls in Section 4 apply to every panel whatever its tier, and until 0.6
opening a project already imports that project's Python previewer drop-ins into
the backend with full privileges (`src/scistudio/previewers/session.py`), which
a sandboxed page does not approach.

Writing back never makes the frontend the record of truth. In the interactive
context the answer travels the existing ADR-051 path — the host sends it to the
backend, the engine resumes the block, and the decision is recorded in lineage
through `block_config_resolved` (ADR-038). For a panel context, the server
acknowledges its one-shot claim and successful completion-event dispatch. The
host waits for that context/workflow/block-matched acknowledgement before closing
the successful interaction or saving interaction memory; rejection and timeout
remain visible errors. This acknowledgement does not change the engine event or
the decision's lineage payload.

## 3. A Panel Is A Folder That Says Where It Belongs

A panel is a directory: a short manifest, the page, and any static files the page
loads.

```text
<tier root>/panels/<panel-id>/
  panel.json      # id, api_version, contexts, types, priority, display name
  index.html      # the page
  panel.py        # optional: the panel's own Python (Section 10)
  ...             # images, styles, scripts the page references
```

The manifest says which contexts the panel was written for and, for previews,
how it competes for a data type.

```json
{ "id": "imaging.image", "api_version": "1.0",
  "contexts": ["preview"], "types": ["Image"], "priority": 100 }

{ "id": "lcms.background_subtraction", "api_version": "1.0",
  "contexts": ["interactive"] }

{ "id": "qc.image_set", "api_version": "1.0",
  "contexts": ["preview"], "types": ["Collection[Image]"] }

{ "id": "lab.threshold_explorer", "api_version": "1.0",
  "contexts": ["miniapp"], "types": ["Image"] }
```

`contexts` exists because the contexts hand a panel different things. A page
written to preview an `Image` expects a typed data object; a block hands its panel
whatever JSON its own `prepare_prompt` built. A preview page opened by a block
would not understand what it was given and would never write back. Declaring the
contexts turns that into an error. This is a statement of compatibility — where
the panel can be used — separate from the permission model of Section 2, which
still decides what the panel can do there.

The preview fields carry exactly what the ADR-048 §3 routing ladder uses. `types`
names the data types the panel shows; an entry of the form `Collection[T]` claims
a collection of `T`, which the ladder treats as its own rung and never hands to a
single-item panel. `priority` breaks ties within a tier and type specificity, as
the imaging and spectroscopy packages already rely on (`priority=100`). The core
tier may also claim the sentinel types `DataObject` and `Collection`, which
implement the core catch-alls. An unresolved tie is still an ambiguity error.
`api_version` states the panel API the page was written against; a page whose
major version the host does not serve is refused with a diagnostic rather than
mounted.

A MiniApp names its data type in `types` as well, but the ladder does not route
it. The user picks a MiniApp by name, and its type decides which data it may be
opened on and which MiniApps a block's context menu offers (Section 11).

The rules are checked twice. When blocks are discovered, a block whose
`interactive_panel` names a panel that is missing or does not declare
`interactive` is refused, the same way ADR-051 already refuses a block whose
capability and execution mode disagree, and the ADR-049 package validator reports
the mismatch before a package ships. Project-tier panels become known only when a
project opens, after blocks are discovered, and a user or project panel may
shadow a non-core panel by id, so the host checks again when it opens a panel: a
shadowing panel that lacks the context it is opened in is refused with an error
naming both panels. A block's declaration keeps its current form — a
`PanelManifest` naming a `panel_id` with an empty `module_url`, the form the
built-in interactive blocks already use — and a non-empty `module_url` is the
deprecated form of Section 8. A panel that declares `interactive` but never writes
back still leaves the block paused, but the host's own Cancel is always present,
so the person is never stuck.

Panels install at the four tiers previewers already use — core, installed
packages, the user library of ADR-053, and the open project — and registration is
the directory itself, so a person or the agent adds a panel by writing files. A
preview panel is chosen by the ladder over its manifest: project over user over
package over core, exact types before parent types, and the per-type user choice
(`src/scistudio/previewers/choices.py`) above all of it. An interactive panel is
chosen by name, because the block that opens it names it, and a MiniApp is chosen
by the user. This ADR accepts the `preview`, `interactive`, and `miniapp` context
values; a later context adds its own.

## 4. The Page Runs In A Sandbox And Reaches The Backend Only Through Its Host

A panel is mounted in an `iframe` with `sandbox="allow-scripts"` and without
`allow-same-origin`. The browser gives the page an opaque origin of its own. The
page can run its script, but it cannot read the application's document, storage,
or cookies, and it cannot make an authenticated call to the backend or read a
backend response. A trusted bootstrap prepended before the panel's markup binds
initialization to that entry document using a per-context proof and private
bootstrap channel. The host transfers input and the canonical message port
through that retained document channel, not the frame's current window; a
navigation before initialization cannot redirect the input to another document.
All panel operations then use the canonical channel, so neither another panel
nor another page can speak to it as the host.

The sandbox alone does not stop a page from sending requests, so three further
controls close the direct paths to the backend. The panel's HTML is served with a
content policy that forbids `fetch`, XHR, WebSockets, and beacons
(`connect-src 'none'`) and limits scripts, styles, fonts, and images to the
SciStudio origin, inline code, and the CDN allowlist of Section 6. The backend
refuses state-changing requests whose origin is opaque, which closes the
"simple request" a page could otherwise send — `POST /api/blocks/reload`, for
example, takes no body and would run without a readable response
(`src/scistudio/api/routes/blocks.py`). And `SCISTUDIO_CORS_ORIGINS`
(`src/scistudio/api/app.py`) may not contain `*` or `null` while panels are
enabled, since either would make every API response readable by any panel.

What these controls protect is the application and the backend's state. They do
not make a panel's data impossible to leak: a page may still request scripts from
an allowlisted CDN, and it can navigate its own frame to another address, which
no content policy prevents. The host tears down a frame that navigates away from
its panel, but the boundary is stated honestly. It is stronger than ADR-048 §8's
"local reliability boundary", and it is still not a guarantee that a panel written
to exfiltrate data cannot do so; that guarantee would forbid CDNs and still leave
navigation open.

The same boundary contains mistakes. A thrown exception or a leaked global
handler stays inside a frame the host can discard and remount. A page that loops
forever freezes the application only if the browser runs the frame in the
application's own process; whether a sandboxed frame gets its own process is a
browser policy, not a property of the `sandbox` attribute, and is verified on the
supported Electron build and browsers rather than assumed (Section 14). Panels are
written mostly by agents, and an agent's first attempt has to be able to fail
without taking the application with it.

A sandboxed page's own requests also carry no login. In the Lab deployment,
SciStudio issues its own session cookie after Hub login and checks it on the UI,
every API, and every static file (`docs/specs/adr-055-enterprise-support.md`); the
browser does not attach that cookie to a module script, font, or fetch requested
by a page with an opaque origin, so a panel's files would be refused. The panel's
files are therefore loaded through a **per-mount token**. When the host opens a
panel, the context service issues a short-lived token that authorizes reading
only that panel's files, the local library set, and the SDK, and the frame loads
from a path that carries it. The page's own relative references inherit the path,
so they carry the token without the page knowing about it, and URLs built from
the host-supplied base path keep working under a JupyterHub user prefix. The token
expires when the context closes. This is the one documented exception to the Lab
deployment's rule that every request authenticates by session cookie: the request
still authenticates, by token, and the token reaches nothing but static files.
Giving panels a separate origin would not avoid this problem — a page on another
origin needs its own credentials all the same — so it is not a reason to prefer
one.

The host implements the operations and the two services over the backend it is
already connected to. A small SDK inside the page turns each call into a
message, and the host answers it:

- `read`, answered from the context's input or by the core read layer of
  Section 5, with numeric data transferred as binary rather than JSON;
- `write back` with a JSON value, present only where the context provides it;
- `call`, forwarded by the host through the backend to the panel's own Python,
  present only where the context provides it (Section 10);
- `sync`, reserved for the notebook context;
- `open` and `save` as described in Section 2;
- housekeeping: signalling readiness, receiving theme tokens and size changes,
  and reporting errors.

The message schema, the shape of each read, and the SDK's delivery are
specification detail; `panel.json` and the SDK become a public surface under
ADR-052 at the `provisional` tier, versioned through `api_version` and a
versioned SDK path because ADR-052's decorators cannot mark a JSON schema or a
JavaScript file. Because everything passes through the host, panels behave the
same in the desktop window, which already runs with `sandbox: true` and
`contextIsolation: true` (`desktop/main.js`), in an ordinary browser, and behind
JupyterHub's path-based routing in the Lab deployment of ADR-055 §8.

Three other placements of the page were weighed. A same-origin frame that is also
allowed to run scripts can reach the host document and remove its own sandbox
attribute, so it isolates nothing; it is today's arrangement drawn inside a
rectangle. A page served from a separate origin is isolated and could fetch data
directly, but every deployment would need a second address brought under its
authentication, and the backend would need a per-context authorization layer for
every data route, not only for static files. Forwarding arbitrary HTTP requests
from the page through the host, checked against a per-context whitelist of
routes, was rejected because it turns every forwarded backend route into a
contract panel authors depend on and ADR-052 must keep stable, and it maintains a
whitelist to express what the context's operations already say.

The frame has costs the specification must handle. Menus and tooltips cannot draw
outside the panel's rectangle; the host's keyboard shortcuts, including Escape on
the full-screen interactive modal, do not fire while the page has focus;
`localStorage`, IndexedDB, and cookies are unavailable at an opaque origin, so a
panel keeps view preferences through the host; `alert`, `confirm`, pop-ups, and
form submission are unavailable; clipboard and fullscreen need explicit frame
permissions; downloads go through `save`; and the page cannot see the
application's CSS or fonts, so the host passes theme tokens (#1849). Because the
page's origin is opaque, the token-scoped routes answer its module scripts and
fonts as cross-origin requests, and their allowlist of file types grows beyond
today's (`src/scistudio/previewers/assets.py`) to include `.html` and common image
and font types.

## 5. Reading Data Needs No Code Of The Panel's Own

Everything a preview panel shows as data lives inside SciStudio's **canonical
zone** (ARCHITECTURE.md §4.3.2). Once data has entered a workflow it is a typed
data object with a storage reference; arrays are stored in Zarr, tables in Arrow
or Parquet, and anything else as a file artifact kept as it is. Types do not own
file formats, and format conversion happens only at IO boundaries (ADR-043 §1).
A small set of bounded reads therefore covers every type: pages of a table, planes
and tiles of an array, decimated series, chunks of text, the slots of composite
data, and the items of a collection. ADR-048 §7 defines those reads, and
`PreviewDataAccess` is where they are implemented; that layer answers a panel's
`read`. Plot-job outputs are the one exception: they live in the preview cache as
display files, not as typed objects (ADR-048 §5), and a panel reads them as files
through the token-scoped path of Section 4.

`PreviewDataAccess` does not yet meet the decision in full, and closing the gaps
is part of this ADR. There is no generic read route — reads reach the frontend
today only through provider envelopes and provider resources
(`src/scistudio/api/routes/data.py`) — so one is added, and with no providers it
becomes the SDK's read contract. Series reads return every point, so they gain the
decimation ADR-048 §7 asks for. Text reads return only the head of a file, so they
gain paging. Collection reads stop at the first page of items, so they gain a
cursor. Artifacts larger than the inline limit cannot be read at all, so they gain
a token-scoped file URL. Tiles are JSON lists of floats, so numeric reads gain a
binary transport. The read budgets for panels are set in the specification and
measured there.

The panel receives values, not pictures, and does its own shaping in JavaScript.
Where that replaces a picture the backend drew, it can be better, not merely
equivalent. The imaging previewer's backend sends its page a plane downsampled to
at most 256 pixels on a side (`PreviewLimits.max_dim`), and the page's contrast
control remaps the pixels of a grayscale PNG the backend encoded from it
(`applyLUTToImage` in the package's `viewer.js`). A panel that reads the plane's
values can adjust contrast across the full dynamic range. The price is more reads:
showing a large plane at native resolution takes many tiles where one small PNG
was sent, which is why the binary transport and the budgets are decisions rather
than tuning.

A panel therefore needs no Python to read. Today a previewer may pair a frontend
module with a Python provider, or consist of a provider alone, and the reason was
that the page could not be customized, so the shaping had to happen on the
backend. The providers in the existing packages bear this out. The spectroscopy
provider reads through `PreviewDataAccess` and pages, filters, groups, and checks
the integrity of bounded rows; its own contract states that those checks perform
no scientific processing. It also renders export figures with matplotlib, which a
panel does in the browser instead. The imaging provider reads through the same
layer and adds downsampling and PNG encoding. Its TIFF and Pillow decoder is a
fallback moved out of core by the hotfix for #1703, and no code path found
produces the non-Zarr image references it serves. All of that work can happen in
the page.

The one need a page cannot meet by itself is a computation over a whole large
dataset — a histogram of an entire image for automatic contrast, a statistic over
millions of rows — because it only ever sees windows. The providers have the same
limit today: they compute over bounded reads and report partial results. When
such reads are needed, they belong in the core read layer as generic reads, not in
per-panel code. An interactive block builds its view in `prepare_prompt`, and a
notebook's kernel owns its variables, so neither context needs one either.
Exploration is different, because there the computation is the point, and
Section 10 gives it a place outside the read layer.

An optional per-panel provider for reads was considered and rejected. It would
bring a Python execution venue that must stay off the API event loop (ADR-048 §8),
a lifecycle, a place in the SDK, and project-tier Python code to trust, in order
to preserve work the page can do. Routing a panel's reads to a different Python
side per context — provider, `prepare_prompt`, kernel — was rejected with it,
because it was the source of most of the model's accidental complexity.
Section 10 does give a panel Python of its own, for a different job: computation
the page cannot do, in a context that asks for it. It pays those costs once, in a
process of its own rather than on the API's, and it never stands between a
preview and its data.

## 6. Built-In Panels Are Ordinary Panels

The viewers SciStudio ships are rewritten as panels and installed at the core
tier: the nine core previewers registered in `src/scistudio/previewers/fallbacks.py`
(`core.dataframe.basic`, `core.array.basic`, `core.series.basic`,
`core.text.basic`, `core.artifact.basic`, `core.composite.basic`,
`core.collection.basic`, `core.plot.basic`, and `core.base.fallback`) and the two
built-in interactive windows, `DataRouterModal` and `PairEditorModal`. They are
served by the same route, mounted in the same sandbox, and given the same
operations as every other panel. They have no privilege a package panel lacks,
while `core.*` ids remain reserved for the core tier. A customized preview copy
uses a new non-core id and the same concrete type, selected through the routing
ladder or the per-type user choice; it does not override the core id. A block
using a customized interactive window names that new panel id explicitly.
Same-id tier shadowing applies only to non-core ids. The collection and
composite panels use `open` to show an item or slot in its own panel, as the
compiled viewers do today. When a panel cannot be loaded, the host shows the
failure and offers the core panel for the type; it does not fall back silently.

The compiled React viewers stay only for what they alone can render until 0.6:
envelopes produced by the Python-only previewers of Section 8. Every new preview
goes through a panel, and the React viewers are removed together with the legacy
contracts. Deleting them sooner would break those previewers before the date
Section 8 promises; keeping them as the renderer for ordinary previews would leave
two rendering paths indefinitely and the most-used views unadjustable.

Panels need libraries — plotting, tables, 3-D rendering, PDF display — and the
frame cannot use the ones the application has already loaded. SciStudio ships a
local set of common libraries at fixed, versioned paths, including a PDF renderer,
because the browser's built-in PDF viewer does not run inside a sandboxed frame.
Built-in panels use only that set, so they work without a network connection.
Custom panels are expected to prefer it, and the agent's context tells authors so,
but they may also load from an **allowlist of public CDNs** kept in SciStudio —
jsDelivr, cdnjs, and unpkg to begin with — enforced by the panel's content policy.
A CDN is fetched by the user's browser, which in the Lab deployment is the
scientist's own computer (ADR-055 §2), so a CDN reference fails only when that
browser is offline or the host is blocked.

This reverses, for panels, ADR-048's rule that "remote CDN imports and arbitrary
external URLs are not part of the contract" (ADR-048 §4, §8, and its rejected
alternative of loading JavaScript from arbitrary URLs, §13), the matching rule of
its specification, and the blocking ADR-049 check that rejects remote frontend
assets (PV-12-001). ADR-048's objection was auditability. The allowlist answers
it: a page can load only from a short list of well-known hosts, versioned CDN URLs
pin what is loaded, and the validator can report every external reference a panel
makes. Allowing any HTTPS host was rejected because it leaves a panel's external
reach unbounded; allowing no CDN was rejected because agent-written pages
routinely reach for libraries the local set cannot anticipate. The versioned
local paths are a contract as well: how long a superseded version stays available
is specification detail.

## 7. What Stays As It Is

Previewers remain read-only. ADR-048 §4 says a previewer must not mutate workflow
definitions, runtime state, lineage, or project files, and the preview context
provides no write back and starts no Python; `save` writes only where the user
chooses.

ADR-051 is unchanged apart from the window contract. An interactive block still
runs in isolated subprocesses on either side of the pause (ADR-051 §3, resting on
ADR-017), with nothing resident while the person decides and a single round of
interaction. `prepare_prompt` runs once when the window opens and still reduces
the data to the view (ADR-051 §2), and the window is still self-contained
(ADR-051 §4): the panel receives that view and reads nothing else. The pause
event is unchanged. ADR-051 Addendum 1's interaction memory is unchanged, and the
interactive window is still the full-screen modal the application draws today.
An interactive panel never runs Python: the interactive context does not provide
`call`, so a panel that declares both `interactive` and `miniapp` runs its
`panel.py` only when it is opened as a MiniApp.

ADR-048's routing ladder, including collection rungs, priority, the ambiguity
rule, and the per-type user choice, and the path confinement of served files
carry over to panels through the manifest of Section 3.

## 8. The Old Previewer Forms Have An End Date

Two existing forms are replaced. The first is an ES module that exports
`mount(container, host)` and is imported into the application's own page —
through `FrontendManifest` and
`frontend/src/components/DataPreview.parts/dynamicPreviewer.ts` for previewers,
and through ADR-051's `PanelManifest.module_url` and
`frontend/src/App.parts/InteractiveModals.parts/panelModuleLoader.ts` for
interactive blocks. The imaging and spectroscopy packages each ship one shared
`viewer.js` for their two previewers, and the LCMS package ships four interactive
panels in this form; the core tutorial "What Is A Type" teaches its review panel
this way. The second is a Python-only previewer: a provider with no frontend
module, whose envelope a compiled core viewer draws. The same tutorial writes one,
`image_preview.py`, into the reader's project and promotes it to their user
library, and the imaging package relies on the path when its module fails to load
and its `kind=ARRAY` envelope degrades to the core array viewer.

Every public symbol involved is `provisional` (ADR-052 §5), so a minor release
could change it with a changelog entry. The owner chose a transition instead. Both
forms stay supported and deprecated, with a diagnostic naming the replacement,
through the 0.5 line, and are removed in 0.6; the current version is `0.3.4a0`.
Their removal, together with the React viewers kept for Python-only previewers
(Section 6) and the backend provider and envelope path, is tracked in #2288.
Until then a legacy module still runs in the application's own page, so the
isolation of Section 4 is complete only once the old forms are gone. The
compatibility paths gain no feature of the new model — no contexts, no
operations — because a shim that grows the new surface becomes a second
implementation that never leaves.

## 9. Writing Back And Syncing Grow By Adding Contexts

Editing data from a preview, and the notebook, are outside this ADR, and the model
is shaped so that neither needs the mechanism to change. Letting a person edit
data means adding a context that provides write back with a defined meaning —
what is written, how a new version is recorded in lineage — and the SDK and the
sandbox stay as they are. A later notebook ADR would define the notebook context,
the semantics of `sync`, and the `notebook` value of `contexts`. An existing panel
takes part in a new context by adding its value to `contexts` and handling what
that context provides; a panel that does not opt in is never opened there. Both
are tracked in #2288. The `miniapp` context is the first such addition, and it
brings the first new operation, `call` (Sections 10 and 11).

## 10. A Panel May Carry Its Own Python

Showing data needs no Python of a panel's own (Section 5). Exploring it often
does. A scientist looking for the threshold that separates cells from background
wants to drag a slider and see the full-resolution stack segmented again each
time; another wants to fit a curve to a spectrum, or to run a function from their
own analysis code on the data in front of them. A page cannot do that over bounded
windows, and pushing the whole dataset into the browser would defeat the budgets
Section 5 depends on. So a panel may carry its own Python.

It is a file, `panel.py`, beside the page, and it is named by its file as
`panel.json` is. The nouns that could have named it are taken: "provider" is the
Python side of the legacy previewers this ADR retires, and SciStudio also uses it
for its AI agent providers; "backend" is SciStudio's own server throughout the code
and this document. The page calls a function in `panel.py` by name through the
SDK — `scistudio.call("threshold", {z: 12, t: 0.4})` — and receives its result.

Whether `panel.py` runs is decided by the context, as everything else a panel may
do is (Section 2). The file is not a permission, and the panel declares nothing
about it. The `preview` and `interactive` contexts do not provide `call` and never
start it, so nothing changes for them: a previewer stays read-only in fact rather
than by convention, and an interactive window stays self-contained, with nothing
resident while the person decides, as ADR-051 §3 and §4 require. The `miniapp`
context of Section 11 provides `call`. A later context — or a later decision to let
previews use it, should a preview need a computation the read layer cannot offer —
provides it the same way contexts grow (Section 9).

Where a context provides `call`, `panel.py` runs in a **resident subprocess**. The
context starts it when it opens and hands it the data the context authorizes, as a
SciStudio data object; the process keeps that data for as long as the context is
open, answers every call, and ends when the context closes. Starting a fresh
process for each call, as a block run does, was rejected because exploration calls
continuously, and a slider that reloads a large stack on every move answers in
seconds rather than at once. Running `panel.py` inside SciStudio's own backend
process was rejected for the reason Section 4 isolates the page: panels are
written mostly by agents, and a first attempt that hangs or crashes must take down
its own process, not the application. Keeping a process resident is what ADR-051
§3 forbids for a paused workflow step, and the difference is deliberate. A paused
step is waiting on a person; a MiniApp is the person's own tool, in use while it is
open.

The process runs on the interpreter and dependency set the user's blocks run on
(ADR-017), from the project directory, so a package the user installed
for their blocks is available to their `panel.py`. It is registered in the
application's process registry (`src/scistudio/engine/runners/process_handle.py`),
the one the commands the agent runs are registered in and that SciStudio's
shutdown ends (ADR-055 §5.3), and it is started and killed as a process group, as
block processes are (ADR-017), so it can be found and ended like them and its whole
process tree is killed with it. It ends when its
context closes — its tab is closed, its project is closed, SciStudio exits, or
the browser that opened it goes away. The last case matters because the backend
keeps running when a browser closes (ADR-055 §7) and a MiniApp tab is not restored
after a reload, so a context belongs to the workspace connection that opened it
and closes shortly after that connection is gone, as runs a browser started are
cancelled today (`src/scistudio/api/ws.py`). A crash is shown in the tab with a
restart action instead of failing silently. An
open MiniApp holds its data in memory for as long as it is open. SciStudio's
resource admission (ADR-022) reserves memory for no process today, so that memory
is measured for diagnostics rather than reserved. Normal MiniApp controls do
not display memory figures. It does count toward the system-memory watermark
at which ADR-022 holds back new block runs.

The page still reaches nothing directly. A call travels over the page's channel to
the host, from the host to the backend on the context's session, and from the
backend to the process; the result returns the same way, as JSON or, for numeric
arrays, as binary, like a read. The page's content policy is unchanged and still
forbids its own requests (Section 4), and the process is not a web server the page
could address.

What the page can reach through `call`, though, is everything `panel.py` offers.
Only functions defined in `panel.py` itself can be called — never a name it merely
imports, such as a library function that deletes files — but every script running
in the page, including one loaded from an allowlisted CDN (Section 6), can call
those functions with the user's reach. The author of a MiniApp decides what
`panel.py` defines, and a page that loads third-party scripts extends that trust to
them.

What changes is the reach of the panel as a whole. The table of Section 2 governs
the page. `panel.py`, where it runs, runs as the user, with the reach of a Code
Block or of a command the agent runs, and nothing confines it to the data its
context authorizes: it can read other files and write new ones. That is the trust
SciStudio already gives the Python of a project's blocks and the code a user asks
the agent to run (ADR-055 §5.3). It is why starting `panel.py` is the context's
decision rather than the panel's, and why the contexts that promise read-only or
self-contained behaviour do not start it.

## 11. MiniApps: An Exploration App The Agent Writes

### 11.1 A MiniApp Is A Panel In The `miniapp` Context

A **MiniApp** is a panel whose `contexts` include `miniapp` and whose `types` name
the one data type it works on. It usually has a `panel.py`. Its page is ordinary
hand-written HTML, the form an agent writes most reliably and can check by
opening it. When the user opens it on some data, the `miniapp` context hands the
page a reference to that data, lets it read that data and its slots or items as a
preview can, and lets it call its own Python; it provides no write back.

A MiniApp leaves nothing behind but itself: its page and its Python, in its panel
directory. It creates no data object and records nothing in lineage, and what its
Python writes is an ordinary file. Exploration is the part of the work that has
not yet become a step, and recording it as provenance would mean keeping an app's
edits, a notebook's code, and a process's variables consistent with one another —
the design this ADR set aside (Section 16). A scientist who finds a step worth
keeping asks the agent to build it, or converts the MiniApp (Section 11.5).

### 11.2 A User Finds A MiniApp And Asks For One

The capability is useful only to a scientist who knows it exists, and most do not
know that the agent can build them a tool. So a MiniApp can be started from four
places, and the product says so in a fifth:

- **The MiniApps tab** of the left sidebar lists the MiniApps available to the
  project as cards, with a New MiniApp button. It takes the place of today's
  Previewers tab, whose list of previewers moves behind an All Previewers button
  in the preview column, where it is looked at in context and opens the same list
  as before; the tutorial steps that pointed at the tab now open the list there.
- **New MiniApp** joins the toolbar's New menu, beside New workflow and New custom
  block.
- **A block's context menu** on the canvas: right-clicking a block that has
  outputs lists the MiniApps that work on its output type and offers New MiniApp.
  Canvas nodes have no context menu today; this adds one.
- **The AI chat** itself. A MiniApp skill, provisioned into each project with the
  agent's other skills (ADR-040), teaches the agent the MiniApp form and
  tells it to offer one when a user's question is better answered by a tool than by
  a single answer, so a user who has never opened the tab can still arrive at a
  MiniApp by describing what they want.

The introduction lives in the rotating tips card at the foot of the left sidebar
(#1997), which exists to tell users about capabilities they would otherwise never
meet. The MiniApps tab itself is only a list and a button.

New MiniApp opens a short dialog with two questions: which data, pre-filled when
it was opened from a block, and what the user wants to see or do. SciStudio then
does three things at once. It creates the MiniApp's directory in the project from
a template whose page explains what a MiniApp is and says that the agent is now
building this one, and opens it in a tab, so the user sees at once that something
now exists and is being filled in. It starts an agent session in the bottom AI tab
(ADR-034) with a brief built from the answers and the MiniApp instructions — the mechanism
ADR-053 §4.1 built for "Bring in my work", in which the product supplies the entry
point, the framing questions, and the instructions, and the agent supplies the
work. And it watches the directory, so that as the agent writes the page and
`panel.py` the open tab reloads and the user watches the app take shape in place. A
session needs a working agent; when there is none, the graded availability of
ADR-053 §5.2 tells the user why and what to do next.

When a MiniApp is made from the chat instead, the agent writes the directory,
checks it with a validation tool, and opens it in the user's workspace with a
second tool. No tool today opens a tab of the agent's choosing: `open_gui` only
returns an address for the agent's own browser, and the only tab the frontend
opens on the agent's behalf is a workflow's, when a run starts or a workflow is
created. Opening a MiniApp follows that pattern — the tool emits a realtime event
and the frontend opens the tab — so the two tools (ADR-040) and the event are
added.

### 11.3 A MiniApp Opens In The Centre Of The Workspace

A MiniApp opens as a tab in the centre of the workspace, where workflows, files,
and previews open. Opened from its card, it asks which block output
to open on and offers the outputs of its declared type; opened from a block's
context menu, it opens on that block's output. It opens on the output of the
block's latest successful run, which is the one SciStudio keeps (#1983), and the
user can later reopen it on the same data or on other data.

While a MiniApp tab is active the right preview column collapses, and it returns to
its width when the user switches to another tab: the app needs the space, and the
column is not a chat, because the AI chat already has its place in the bottom
panel. The tab is of its own kind. A preview tab is dropped as soon as another tab
becomes active; a MiniApp tab stays open while the user moves between tabs,
because closing it ends its process and its state. Its toolbar carries restart,
stop, and the conversion of Section 11.5. The narrow AI-host presentation of
ADR-055 §6 has no right column and shows the preview as a card in the sidebar, so
there nothing collapses and All Previewers sits in that card.

### 11.4 MiniApps Live Where Panels Live

A MiniApp installs at the four tiers every panel uses (Section 3): core, installed
packages, the user library, and the project. A new MiniApp is created in the
project, whose git history keeps it (ADR-039), and a package can ship MiniApps for
its data types. A card in the MiniApps tab carries the hover detail popover a block
card carries — the shared popover of ADR-053, showing the MiniApp's description,
its data type, and where it lives — and, for a MiniApp in the project, the Promote
to My Library action, so that a tool made in one project can be used in all of
them. Promotion keeps the rules of ADR-053's personal tool library specification: it
is a move (FR-017), it is offered only for items that live in the project
(FR-019), and it shares one implementation with the other promotion entry points
(FR-025). It is extended from a single file, which is all it
handles today, to a panel directory.

### 11.5 An Exploration Becomes A Workflow Step Through The Agent

A MiniApp that proves useful often suggests a step the workflow should take every
time — the threshold the scientist settled on, the regions they picked. That is
the shape of an ADR-051 interactive block, a window that shows real data and
returns a decision, so a MiniApp tab offers Convert to interactive block. It asks
what output the block should produce and then starts an agent session that
writes an interactive block from the MiniApp, leaving the MiniApp in place:
`prepare_prompt` builds the view, the MiniApp's page becomes the basis of the
block's interactive panel and writes back one decision, and `run` computes the
outputs from it.

The conversion is the agent's because it cannot be mechanical. A MiniApp calls its
Python whenever the user moves a control, while an interactive block's window must
be self-contained, with nothing resident during the pause and a single round of
interaction (ADR-051 §3, §4). Deciding which part of an app is the decision, what
the view must contain, and how to rewrite the live calls requires reading the
code. Requiring every MiniApp to be written from the start as view, decision, and
compute, so that the conversion could be mechanical, was rejected: every MiniApp
would carry that structure, and many explorations have no decision at all.
Amending ADR-051 to keep a Python process through the pause was rejected because
it would give up the property ADR-051 §3 exists to protect.

## 12. Scope

In scope: the panel concept, its operations, and the `open` and `save`
services; the context model and the table of Section 2 as the permission model;
`panel.json` with `api_version`, `contexts`, `types`, and `priority`, and the
discovery-time and open-time checks of Section 3; the sandboxed frame, the
channel-bound SDK, the content policy, the backend's refusal of opaque-origin
state changes, the CORS restriction, and per-mount tokens of Section 4; the

`call` operation, and the resident process of Section 10; and the `miniapp`

an interactive block.

Out of scope, each tracked in #2288: editing data from a preview or any context
beyond an interactive block's decision; the notebook context and `sync`;
Python for preview and interactive panels; lineage records for what a MiniApp
computes; reserving memory for resident processes, which ADR-022's resource
manager does for no process today; editing a panel's source inside the
application rather than as files on disk; and migrating the external packages,
which happens in their own repositories.

## 14. Verification And Tooling Impact

This ADR is documentation-only; implementation and its tests land in the
implementation PRs tracked in #2288 and coordinated under #2296, where MiniApps are
a fourth phase after the first three.

The decision is verified where each guarantee lives:

- **Sandbox and direct paths.** Every panel mounts in a frame without
  `allow-same-origin`; a page cannot read or change backend state directly — its
  fetches are blocked by the content policy, a simple state-changing request from
  it is refused by the backend, and `*` or `null` in `SCISTUDIO_CORS_ORIGINS` is
  refused while panels are enabled; a frame that navigates away is torn down.
- **Messaging.** Messages from anything but the panel's own channel are ignored.
- **Permissions.** A preview panel has no write back and cannot read outside its
  target and the target's children; an interactive panel receives only the
  block's view and writes back exactly once; `open` works only for children.
- **Manifest.** An empty or unknown `contexts`, a `preview` panel without
  `types`, an unserved `api_version` major, and a block naming a panel without
  `interactive` are refused at discovery and by the ADR-049 validator; a
  shadowing panel lacking the context is refused when opened. Collection rungs
  and priority route as ADR-048 §3 describes.
- **Lab.** A panel with module scripts, fonts, and library imports loads through
  the Hub proxy under a user prefix using its per-mount token, and the token is
  refused after the context closes and for anything but static files.
- **Containment.** A page that loops forever is tested on the supported Electron
  build and browsers, and the result is recorded.
- **Built-ins and migration.** Built-in panels resolve through the same route and
  ladder as package panels and render with no network access; legacy modules and
  Python-only previewers still load, with a deprecation diagnostic, until the
  release that removes them.
- **Python only where a context starts it.** A panel with `panel.py` opened in a
  preview or an interactive context starts no process and offers no `call`.
  Opened as a MiniApp it starts one process, registered in the process registry,
  which ends with its whole process tree when its tab, its project, or SciStudio
  closes; a crash is shown in the tab.
- **Calls.** A `call` reaches `panel.py` only through the host and the backend,
  and the page's own requests are still refused.
- **MiniApp entries.** Each of the four entries leads to the create dialog or to a
  MiniApp; submitting the dialog opens the template tab at once, and the tab
  reloads as the agent writes files; a block's context menu lists exactly the
  MiniApps for its output type; the agent's tool opens a MiniApp tab; the preview
  column collapses and returns; All Previewers opens the list the Previewers tab
  showed.
- **Promotion and conversion.** Promoting a project MiniApp moves its directory to
  the user library, where it stays available; conversion starts an agent session
  that carries the outputs the user chose.

## 15. Consequences And Risks

SciStudio gains one mechanism where it had two. A panel is one HTML page and a
short manifest, which is the form an agent writes most reliably and can check by
opening the page with sample data. Built-in viewers become adjustable, a faulty
page can no longer reach the application's state, and the same panel runs in
every deployment.

The cost is concentrated in migration. Every built-in viewer and both built-in
interactive windows are rewritten. The imaging and spectroscopy packages move
their frontends into panels and port their provider shaping — about 1,570 lines
of Python across the two, including server-side export figures — to JavaScript;
the LCMS package moves four panels; the tutorial that teaches both old forms is
rewritten. Two loaders and the React viewers coexist until 0.6, and legacy
modules stay unsandboxed until then.

The mechanism adds pieces of its own: the generic read route and its extensions,
per-mount tokens and the documented exception to the Lab deployment's cookie rule,
the content policy and CDN allowlist, and the backend check on opaque-origin
requests. The frame costs some polish (Section 4). Reads that used to be a function
call inside the page become message round trips, and native-resolution views need
more of them, which the binary transport and the budgets must keep acceptable. The
local library set becomes a versioned contract that must be maintained, patched,
and licensed. A custom panel that relies on a CDN fails when its user is offline.
And the boundary protects the application, not the confidentiality of what a
panel is shown (Section 4). The public surface changes: the provisional manifest
types are retired on the schedule of Section 8, and `panel.json` and the SDK
become the new author-facing surface under ADR-052.

MiniApps give exploration a place in SciStudio and put the agent's ability to
build tools where a scientist will see it. They carry costs of their own. An open
MiniApp keeps a process and its data in memory until it is closed; resource
admission reserves nothing for it, though its memory counts toward the watermark
that holds back new block runs. Its Python runs as the user, so a MiniApp is not
read-only, and what it does to the user's files is as trustworthy as the agent
that wrote it. Every MiniApp is bespoke code, and none can be made without a
working agent. Exploration leaves no lineage by design, so how a scientist
arrived at a step is recorded only once they turn it into one. The feature adds
surfaces SciStudio must keep — a tab kind, a canvas context menu, a create flow
and its template, agent tools with a realtime event, a skill, and directory
promotion — and `panel.py` and `call` join `panel.json` and the SDK as
author-facing surface under ADR-052. Moving the previewer list from its own tab to
a button in the preview column changes where existing users, and the tutorials
that point at the Previewers tab, find it.

## 16. Alternatives Considered

**A same-origin frame.** Rejected because a frame allowed both scripts and its
host's origin can remove its own sandbox, so it isolates nothing.

**A separate origin for panels.** Rejected because every deployment would need a
second address brought under its authentication and the backend would need
per-context authorization on every data route; it would not remove the login
problem that per-mount tokens solve.

**Forwarding arbitrary HTTP requests through the host against a route
whitelist.** Rejected because forwarded routes become a stable contract and the
whitelist restates what the context's operations express directly.

**Loading panel files with cookies only, or injecting them from the host.**
Loading only through classic tags that carry cookies was rejected because module
scripts, fonts, and fetches never carry them and browsers keep tightening cookie
rules. Having the host fetch files and inject them into the frame was rejected
because it breaks relative references and module imports and forces every panel
into a single file.

**Permissions declared by the panel, or granted by install tier.** Rejected
because the context already knows what a panel may do, and a permission
vocabulary is a second contract to maintain.

**Interactive panels reading the block's inputs by reference.** Rejected because
it would amend ADR-051 §2 through §4 and send data the block chose not to send.

**An optional Python provider per panel for reads, or per-context routing of a
panel's reads to a Python side.** Rejected because canonical storage makes bounded
reads sufficient and every other context already has its Python side. The
`panel.py` of Section 10 is not a read provider: it serves computation, and only
where a context starts it.

**Nested panel frames for collection and composite children.** Rejected in favour
of `open`, which keeps today's drill-down behaviour without frames inside frames.

**Keeping the built-in viewers as compiled React components, or deleting them
before 0.6.** The first keeps two rendering paths and leaves the most-used views
unadjustable; the second breaks Python-only previewers before their end date.

**Libraries from any HTTPS host, from no CDN, or bundled by every panel.** Any
host leaves external reach unbounded; no CDN blocks libraries the local set cannot
anticipate; bundling duplicates libraries in every panel.

**Declaring the `notebook` context now.** Rejected because a context value that
nothing can yet open is untestable; a later notebook ADR would add it.

**Removing the old forms immediately.** Rejected because installed packages, user
projects, and a core tutorial depend on them; they end in 0.6 instead.

**Python only for MiniApps, as an exception to the panel model.** Rejected in
favour of a capability every panel has and each context decides whether to use,
which keeps one model and leaves a later decision free to let previews use it.

**An application framework — Streamlit, Gradio, marimo, Shiny, or HoloViz Panel.**
Each can now be mounted in a FastAPI application, but with any of them the
framework generates the page instead of the agent writing it; the page keeps a
live connection to the framework's own server, which the panel sandbox forbids,
so it would become a second page system beside panels; and mounting it runs the
app's code in SciStudio's own process.

**A notebook beside a panel.** Opening a notebook and a kernel on a block's output,
with a panel that writes its edits into the notebook as code and follows the
kernel's variables, was designed and set aside. Each question it raised — how an
edit becomes code, how that code stays reproducible, how a variable finds its
panel — belonged to a generic contract between two general tools. A MiniApp's
page and Python are written together for one purpose and need no such contract.

**A fresh process for each call, or `panel.py` inside SciStudio's process.** The
first is too slow for continuous interaction and the second lets an agent's first
attempt take the application down (Section 10).

**Converting a MiniApp mechanically, or keeping its Python alive through an
interactive pause.** Rejected in Section 11.5.

**Keeping the Previewers tab and adding a MiniApps tab beside it.** Rejected
because the previewer list is consulted about the preview in front of the user,
which is where the All Previewers button puts it, and the sidebar slot is better
spent telling users that MiniApps exist.

**A separate ADR for MiniApps.** A MiniApp is a panel in a new context, with Python
and entry points around it, and this ADR's contexts are its extension point, so it
is recorded here.
