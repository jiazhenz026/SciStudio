# ADR-054: Explore Sessions And One Contract For Interactive Panels

## 1. Decision Summary

A scientist runs the first three blocks of a workflow, looks at what came out,
and does not yet know what the fourth block should be. Finding out means trying
things: filtering on a column to see whether the effect survives, changing a
threshold to see how many peaks it keeps, plotting one channel against another
because a colleague mentioned it. None of this is known in advance, which is
precisely why it is being done. Some of it is written as code; some of it is
done by dragging a region on a plot or picking rows in a table. Either way it is
exploration, and exploration is where a workflow gets discovered rather than a
step inside one.

This ADR gives that exploration a home and, in doing so, unifies the surfaces
SciStudio already has for looking at data and for interacting with it.

**An Explore Session is a notebook and a live kernel opened over some data.**
The data is the output of a block that has run, or a file in the project. The
session is a file in the project, on the branch that holds the data context it
explores (§4.5). It is not a node, it does not appear on the canvas, and neither
the engine nor a pause is involved while a person explores.

**A notebook worth keeping is packaged into a block.** When the person judges
that what they have written is the fourth step, they package it. The result is
one block: its ports are the inputs and outputs the notebook declares, it
executes the backward slice of its declared outputs with no interface and no
kernel held for a person, and on new data it replays. The notebook is never
split into a subgraph and no structure is inferred from code (§4.6).

**One panel contract serves display and production.** A panel that only
displays is what ADR-048 calls a previewer. A panel that produces a value is
what an interactive block opens. Both become one contract (§3), the same panel
serves either, and every panel SciStudio ships — the built-in ones included —
is a document on disk that a person can edit.

**One surface hosts every interaction.** An interactive block that pauses opens
the same Explore tab that exploration uses, with its panels bound to the run's
inputs and the notebook pane absent (§4.2). The modal it opens today is retired.
What a block remembers across runs becomes one setting — replay, or ask again —
rather than two mechanisms (§4.7).

The design has one axis where its first draft had two. A panel displays or
produces; that is the whole of it. Whether the code behind a step was written by
a block author or by the person in a notebook is a property of the block, and
the surface the person interacts with is the same for both.

The sections that follow define the panel (§3), the session and packaging (§4),
the kernel (§5), and the notebook (§6). Lineage (§7) records what happens in a
session and what a packaged block records; §8 covers what the agent has to be
taught, since the agent writes most of the panels, blocks, and cells this design
expects. §9 states the code shape the unification requires, because a
unification that lands as a third parallel module is not one.

This ADR was revised on 2026-09-02, while still Proposed, to state the session
model as the owner intended it. §13.1 records the shape it replaced.

### 1.1 Problems Addressed

## 2. Interaction, Extended

ADR-051 §3 records the shape of an interactive step. A block declares the
interaction capability and an execution mode; a prompt phase turns the real
inputs into a window-sized view and exits; the engine holds a pause; a fresh
subprocess computes the block's outputs from the decision the person made. The
governing concern is that a person may take a second or an afternoon, so the
wait must cost nothing and weaken nothing: no block code resident, isolation
preserved, cancellable throughout.

That shape is kept exactly. This ADR changes three things around it.

**Where the interaction is shown.** The pause opens the Explore tab (§4.4)
rather than a modal. The panels are the same panels, bound to the run's inputs
through the same host; confirming and cancelling are actions on the tab. The
engine notices nothing.

**What a panel is.** ADR-051's panel is named by its block and returns a
decision. ADR-048's previewer is routed by data type and returns nothing. One
contract now covers both, so a panel written once is available wherever its
data type appears (§3).

**What the person may do once they are there.** ADR-051's person answers a
question. This ADR's person may also open a notebook and a kernel over the same
inputs, explore, and package what they find into a block (§4.2, §4.6). Nothing
about that touches the paused block: it still receives its decision or is
cancelled, and its compute phase is unchanged.

**What does not change.** Existing interactive blocks continue to work without
modification; their compute phase, their isolation, and the guarantee ADR-051
was written to protect apply unchanged. A kernel exists only while a notebook
is open, is owned by the session service, and is never the engine's (§5.3).

## 3. The Interactive Panel

### 3.1 One Contract, Two Capabilities

SciStudio has two dynamic panel loading paths. The previewer loader validates a
manifest, imports an ES module from a backend-validated same-origin URL, reads a
named export, checks an API version, and mounts it with a read-only host API
(`dynamicPreviewer.ts`, ADR-048 FR-022/FR-023). The interactive-block panel
loader does the same sequence against a different asset route and hands the
module a way to confirm or cancel (`panelModuleLoader.ts`, ADR-051).

What has diverged without cause is the machinery below the surface: two copies
of the load sequence, two API version constants, two asset whitelists, and two
different things happening when a module fails to load.

The loaders collapse into one contract whose panels declare one of two
capabilities.

A **displaying** panel renders what it is given and has no outbound path. This is
what a previewer is today.

A **producing** panel renders what it is given and can hand back a value — a
selected region, a chosen item, a threshold. The value's meaning is settled by
where the panel is mounted, which is what lets one panel serve both places. In
an interactive block's pause the value becomes the decision the block's own code
consumes. In a session with a notebook open it becomes a line of code appended
to the notebook and executed. A panel author writes the region picker once and
does not choose where it will be used.

### 3.2 The Authoring Form

A panel is **one self-contained HTML file** — markup, styles, and script in a
single document — mounted in a sandboxed `iframe` and reachable only through
`postMessage`. The frame is granted script execution and nothing else, so it
runs at an opaque origin and cannot reach the application's document, its
storage, or its API; the one thing it can fetch on its own is the read-only
asset route, which answers it as a cross-origin request.

The form is chosen for who writes these panels. A panel that ships with a
package is written once by a package author, and a panel belonging to a project
or a user library is, in practice, written by the agent on the user's behalf;
ADR-053 §4 records the same conclusion for blocks, and there is no visual panel
editor planned. Authoring by an agent has two requirements that dominate every
other consideration. The agent must be able to **see whether its output works**,
which a plain HTML file satisfies by opening in a browser with stub data and
which no kernel-coupled widget format satisfies. And the agent's first attempt
must be able to **fail without consequence**, which the frame boundary provides:
a runaway loop, a leaked global handler, or a thrown exception is contained in
the panel that caused it. Plain HTML is also the single most widely represented
UI form there is, so the agent writes it from a far deeper well of examples than
any framework-specific alternative offers.

The frame boundary carries a second benefit that grows with session length. A
session runs for hours with several panels mounted, and a panel
that leaks memory, captures the keyboard, or bleeds CSS into the application
would degrade the whole workspace if it shared a realm with it. Containment
costs nothing extra once the boundary exists for authoring reasons.

The cost accepted in exchange is that **panels render only inside SciStudio**. A
notebook carried to JupyterLab or Colab still executes every line of its code
and still describes its own inputs; what it loses is the interactive surface,
which is SciStudio's own contribution rather than something the person brought
with them. The `.ipynb` format of §6.5 delivers portability of the analysis; the
panels were never portable value.

### 3.3 How A Panel Is Found

Discovery differs by what is being opened, and the differences are legitimate.

A displaying panel is routed by the type of the data being shown, so it uses the
ladder that resolves project over user over package over core across exact and
ancestor matches (`previewers/router.py`), together with the per-type user
choice added by #2017 and #2049.

A producing panel opened by an interactive block is named by that block —
`InteractiveMixin.interactive_panel` is a `PanelManifest` declared on the class —
so it is discovered exactly as its block is and inherits the block tiers,
including the user library. No routing question arises.

A producing panel bound to a notebook variable is routed by that variable's
type, which puts it back on the first ladder.

Each case keeps the mechanism appropriate to it and shares the loading,
versioning, and failure behaviour that none of them had a reason to own
separately.

Every request to open a panel states the capability it needs, displaying or
producing. Candidates are filtered by that before the ladder and the user
choice apply, and the choice is kept per type and per capability, so the panel
a person prefers for looking at a frame and the one they prefer for producing
from it can differ. A block that names its panel must name a producing one,
and that is checked when the block is discovered.

On disk a panel is a directory holding a manifest and its document:

```
~/.scistudio/panels/table-editor/
  panel.json     # id, display name, target types, declared capability, entry file
  index.html     # the self-contained document
```

The four tiers are the ones `core/dropins.py` and `core/origins.py` already
define for blocks, types, and previewers (ADR-053 FR-057/FR-060): a core set, a
package set discovered through entry points, `~/.scistudio/panels/`, and
`{project}/panels/`. Registration is the directory: a package points its entry
point at the panel directories it ships, and the user library and the project
contain theirs. No tier constructs a Python object to register a panel, which
is what lets a person or the agent register one by writing files. A panel may
name a Python provider for a type the shared data-access layer cannot window;
otherwise it needs none. The existing `previewers/` directories keep working
through the migration in §10.1.

The core tier is a directory on disk as well. The panels SciStudio ships built
in — today's nine previewers and two interactive panels — are rewritten as panel
directories under the panel subsystem and served through the same route, with
the same path confinement, as every other tier; their Python providers are
unchanged. A built-in panel can therefore be shadowed by the user library or the
project, and copying one is a directory copy. The frontend keeps no mapping from
a response's kind to a component: the backend names the panel, and the fallback
panel, in the response it already sends.

### 3.4 What The Host Supplies

Across the `postMessage` boundary the host hands a panel what it is displaying —
for a displaying panel, one target; for a producing panel bound to notebook
variables, a map from variable name to type and current snapshot — along with a
bounded windowed read, the outbound path its declared capability earned, an
update callback carrying the reason and what changed, and an error channel.
Panels bound to a notebook bind **multiple variables**, because comparing
a spectrum against a table is the ordinary case rather than an advanced one.

Message passing costs little here because the contract is already asynchronous
end to end: a windowed read is a server round trip, a produced value waits on
the execution queue, and updates arrive as pushes. Only the opening snapshot is
synchronous, and it is delivered once at mount.

Reads are windowed for the same reason previews are: a bound variable may be
larger than the frontend can hold. The existing bounded data-access layer under
`scistudio.previewers.data_access` supplies the mechanism, so the panel receives
the page it is displaying rather than the object. A panel that needs bulk data —
an image plane, a long trace — fetches it from the same-origin asset route
directly, which keeps large payloads out of both the message channel and the
application's own memory.

### 3.5 Editing A Panel

A person can change any panel, including the built-in ones. The editing model is
copy-on-write over the tier ordering of §3.3. Saving an edit writes back to the
tier the panel was resolved from. Core and package panels are read-only, so
editing one copies it into the open project under the same id, and the ordering
is what makes the copy take effect. The system does not ask where to save. A
project sits under git, so an edited panel travels with the workflow it belongs
to.

Saving reloads the panel: every mounted instance is torn down and remounted
from the new document, without the person reopening anything. The frame
boundary makes this clean, since discarding a frame leaves no cached module
behind. An optional state hook lets a panel hand the host a serialisable
snapshot before teardown and receive it on remount, so a drawn selection
survives a change to the button beside it; a snapshot that will not serialise is
discarded and the panel remounts clean.

An edit that breaks the panel is reported explicitly, with a diagnostic naming
the panel and the failure, and the host offers to revert by deleting the
shadowing copy. It does not silently fall back to the panel that was shadowed,
because a silent fallback reads as an edit that was never saved. The data stays
visible throughout, through the fallback panel the backend names.

The reload trigger fires for files the agent writes on the person's behalf as
well as for files the person writes. The file watcher suppresses files the
product itself has written, and an agent-written panel must not fall into that
category.

### 3.6 What A Panel May Emit

A producing panel's only outbound path is the emission of code, and the meaning
of what it emits is settled by where it is mounted. In a session with a notebook
open, the emitted code is appended as a cell and queued. The dependency analysis
of §6.2 depends on that code rebinding names rather than mutating objects in
place, and a convention to that effect would be a promise no one could check.

The check is mechanical and sits at the one point every emission passes. Before
an emitted snippet is queued, the host parses it and admits only these statement
forms: assignments whose every target is a plain name, including a tuple or
star unpacking of plain names; imports; and calls to `scistudio.output`. An
assignment to a subscript or an attribute is refused, because it mutates the
object the name holds rather than rebinding the name, which is exactly what the
rule exists to prevent; a panel that changes rows emits `df = df.drop(...)`, not
`df.iloc[i] = ...`. Any other statement form is refused with an error naming the
panel and the statement. A panel cannot mutate the session's data directly,
since it holds no Python object and can only send a string; the whitelist closes
the one way a string could do so. The residual case, an assignment whose
right-hand side has a side effect, is the same hole hand-written code has, and
§6.2 bounds it.

A displaying panel emits nothing. Giving the plot panel the producing capability
— dragging an axis or a region and having the plot re-render from emitted code —
is real value and is deferred to a tracked issue (#2212) rather than folded into
the migration.

## 4. The Explore Session

### 4.1 A Session Is Not A Node

An Explore Session is opened over data. The person right-clicks a block whose
outputs exist and chooses to explore them, or right-clicks a file in the
project's data tree. What opens is a notebook and, once the person runs a cell,
a kernel (§5). Nothing is added to the workflow: no node appears on the canvas,
the engine is not involved, and there is no pause to release. A session is a
way of looking at data the project already holds.

The notebook is a file in the project, on the branch that holds the data
context it explores (§4.5), and every cell run is committed (§6.6). Exploration
therefore has a home and a history from the first cell, whether or not anything
comes of it.

The session's inputs are named in the notebook itself. Opened from a block's
outputs, the first cell loads each output port into a variable named after the
port; a block with several outputs contributes them all, and the person deletes
the lines they do not need. Opened from a file, the first cell loads the file.
The difference matters only at packaging (§4.6), where a file load becomes a
port. A block whose outputs have never been produced has nothing to explore, and
the action is not offered.

### 4.2 One Surface For Every Interaction

The first draft of this ADR distinguished two kinds of session — one in which
the block's code is fixed and the person supplies a value, one in which the
person writes code — and described the interaction surface separately for each.
There is one surface. The Explore tab (§4.4) hosts panels bound to data; a
notebook pane is present when the person is exploring and absent when an
interactive block is asking its question. The panel host, the bindings, the
confirm and cancel actions, and the kernel list are the same in both cases.

An interactive block's pause opens the tab with its panels bound to the run's
inputs and no notebook. The person confirms, and the block's compute phase runs
from the value the panel produced, exactly as ADR-051 specifies. The modal that
opens today is retired.

From that paused state the person may open the notebook pane. A kernel starts
over the same inputs, and what follows is exploration. Whatever they write does
not change the paused block: if it is worth keeping it is packaged into a new
block (§4.6), and the paused block still receives its decision or is cancelled.

What differs between an authored interactive block and a packaged notebook block
is the code, and that is a property of the block. The one runs its author's
Python in a fresh subprocess from a decision value; the other runs the
notebook's declared-output slice. Neither is a kind of session.

### 4.3 Inputs And Declared Outputs

A session reads its inputs from the data it was opened on, and the notebook's
first cell says so:

```python
df = scistudio.load(scistudio.input("data")).to_pandas()
```

Writing the load into the notebook rather than injecting a variable behind the
person's back is what makes everything downstream work. The notebook replays
from a cold kernel, so a crashed or restarted kernel is recovered by re-running
rather than by special machinery. Once packaged, it executes against whatever
the port supplies, so the same notebook runs on a different batch without
editing (§4.5). It opens in Jupyter and still describes its own inputs. A session
opened from a file writes `scistudio.load("<path>")` instead, and packaging
rewrites that line into a port read.

Outputs are declared in the notebook as well:

```python
scistudio.output(peaks=peaks, table=df_clean)
```

Declaring in code rather than in interface state keeps the declaration inside
the artefact that travels, and it obeys the rule in §3.6 that a panel's effect on
a notebook is always a line of code. While a person is working, the call marks
those bindings as durable and pins their panels (§4.4); at packaging it names
the block's output ports; in a packaged block's run it writes them.

### 4.4 Where A Session Appears

The frontend already models the centre area as a discriminated union of tabs —
`WorkflowTab | FileTab | PreviewTab`, where the preview tab was added by #2112.
An Explore tab is one more member of that union, and it is the surface for
every interaction (§4.2). Double-clicking a packaged block's node opens its
notebook in this tab, extending the affordance ADR-044 already gives a
subworkflow node, whose double-click opens the file it references.

The layout is the workspace's own. The left pane is unchanged: the palettes,
the project tree, and the data tree are what a person needs while exploring,
and the block cards are where the blocks callable from a cell (§5.5) are found,
by adding a card to that panel. The centre is the panel host. The right pane
holds the notebook, replacing the data preview while the tab is active; the
panels in the centre are the preview of what the notebook binds. The bottom
panel is unchanged.

Across the top of the centre runs a variable strip: every top-level name the
dependency analysis (§6.2) finds bound in the notebook, with its type. The
strip is populated from the analysis, so it lists `df` as soon as the first
cell exists; a name whose object does not yet exist in the kernel is shown and
cannot be opened. Nothing runs by itself, and the first cell runs when the
person runs it. Clicking a name opens a panel over it in the centre; names
declared as outputs are opened and pinned automatically. A notebook accumulates
dozens of bindings, and opening all of them would bury the ones that matter.

The tab's toolbar carries the session's controls: run the stale set (§6.1),
interrupt, restart, package (§4.6), and a collapsible list of every kernel alive
in the project with the session it belongs to, the memory it holds, and a way
to end it. That list is what makes a resident kernel attributable (§5.3)
without a dedicated surface.

Inside the tab, a secondary view renders the session's **dependency graph** —
one node per variable version, edges from the analysis in §6.2. The linear
notebook cannot show that two filters are siblings rather than successive
steps, cannot show which results are stale, and gives a subgraph selection
nowhere to live.

### 4.5 The Branch A Session Belongs To

ARCHITECTURE.md §4.6 describes how branches are used here: one branch carries
one data context — a batch, an instrument, a cohort — along with the workflow
variant adapted to it, and merging is usually beside the point. A session's
notebook is a file on such a branch and travels with it, so the exploration of
one batch sits beside the workflow that batch is analysed with.

Adapting a packaged block to a new data context therefore uses the mechanism
the project already has for adapting a workflow: branch, wire the node to the
new context's data, and run. The port-based first cell of §4.3 is what makes
the rest of the notebook carry over untouched, and §4.7 is what makes it replay
rather than reopen.

Switching branches while a session is open **retires the kernel**. The kernel
holds one context's data, and the branch switch means the person is now working
on another; carrying the objects across would produce a session whose memory and
whose files disagree. Retirement is inexpensive because the notebook replays.
This is stated explicitly because branch switching under live application state
has already produced defects in this product (#1872).

A branch may hold **several sessions**, since one data context can reasonably be
explored from more than one angle at once.

Carrying an improvement from one data context to the others is a **subgraph
operation** rather than a text merge. The person selects a connected region of
the dependency graph, and its inputs are rebound to the corresponding versions
in the target session. This is what the graph view of §4.4 exists to make
selectable.

### 4.6 Packaging A Notebook Into A Block

When the person judges the notebook worth keeping, they package it. Packaging
produces one project-local block. Its input ports are the notebook's
`scistudio.input` reads and its output ports are its `scistudio.output`
declarations, both read by the analysis of §6.2, and its implementation is the
notebook. The block appears in the project's block palette and is placed in a
workflow like any other block. Making it available across projects is the
block-library promotion ADR-053 already provides.

Packaging refuses a notebook whose declared-output slice contains a stale cell
(§6.1) or an unresolved read, and says which. It refuses a notebook that calls
an interactive block from a cell (§5.5), because such a notebook cannot run
without a person.

The packaged block runs the backward slice of its declared outputs (§6.7). On
new data it replays without pausing (§4.7). Double-clicking its node reopens the
notebook in the Explore tab, bound to the node's most recent run inputs, and
changes are packaged again. The block owns its copy of the notebook, and the
exploration it came from continues on its own; the two may diverge, which is
the ordinary relationship between a scratch history and a product.

What packaging does not do is turn a notebook into a subgraph. The first shape
of this design tried that and was abandoned for the reasons §13.1 records:
splitting statements into nodes, guessing which branches were intentional, and
inventing canvas positions. Packaging makes one block and infers nothing. A step
in the notebook that already calls a block is recorded as a block call (§6.4);
lifting such calls onto the canvas as nodes of their own would be exact rather
than inferred, and is left for a later decision.

### 4.7 What A Block Remembers

ADR-051 remembers an interactive block's decision and, through
`remap_saved_decision`, replays it only when the input fingerprint is
unchanged. That is right for a decision that names an item: the person chose
the third image, and a different batch has a different third image. A packaged
notebook block is the opposite case — running the same analysis on new data is
the entire purpose — so it replays across changed inputs.

The two are one setting rather than two mechanisms. Every block with an
interaction declares what happens on new input: **replay** the remembered
decision or notebook, or **ask** by opening the Explore tab with the panels over
the new inputs. A packaged notebook block defaults to replay; an authored
interactive block defaults to ask; either default can be changed on the block.
`remap_saved_decision` is the implementation of ask. Left as two mechanisms, the
symptom would be a packaged block that reopens for exploration every time the
batch changes, with the cause buried in a base-class default.

## 5. The Kernel

A session with a notebook has one; an interactive block asking its question
does not.

### 5.1 The Interpreter

The kernel is an `ipykernel` process launched from SciStudio's **bundled
Python**, the same interpreter and the same dependency set the workflow runtime
uses.

The failure this avoids is specific and expensive: an analysis that works while
a person is exploring and fails when the same notebook runs as a packaged
block. Both execute the same code on the same data, so a difference in
interpreter would be the only way they could disagree, and it would arrive as a
loss of trust in the mechanism this ADR is built on.

Using `ipykernel` rather than a bespoke execution loop follows from who the
users are. They know Jupyter, which means they expect `%pip`, `%%time`, and the
rest of the magic vocabulary to work, and they will type them whether or not
they are supported.

### 5.2 Objects At The Boundary

The kernel holds **native objects**. `df` is a `pandas.DataFrame`, an array is a
`numpy.ndarray`, and the SciStudio type layer supplies the conversions at the
boundary — `DataObject.to_memory()`, `DataFrame.to_pandas()`, `Array.to_numpy()`
on the way in, and construction from `data=` on the way out. Handing the person
SciStudio's own wrapper types would make every line of generated code unfamiliar
and would put a translation step in front of a packaged block's run. Users of this
feature know pandas; the product gains nothing by standing between them and it.

### 5.3 Who Owns The Kernel

ADR-051 §3 requires that a paused step hold no block code or data resident, and
ADR-051 §9 explicitly rejected keeping the prompt-phase worker open across the
wait, because it would pin resources and storage handles for the whole human
wait and complicate cancellation. A session's kernel is a resident process, so
the relationship needs stating rather than glossing.

The two do not meet. A session is not a workflow step (§4.1), so while a person
explores there is no pause and nothing of the engine's is waiting. The kernel is
owned by the **session service**, which sits beside the engine and never inside
it. When an interactive block's pause opens the Explore tab (§4.2), the panels
read the run's stored inputs through the host and no kernel exists; the engine
holds its pause the way it always has, with nothing of its own resident. A
kernel appears only if the person opens the notebook pane, and it is the session
service's kernel over a copy of those inputs, which the engine neither knows
about nor waits for. Isolation is therefore preserved in the direction ADR-051
cared about: the engine cannot be hung, leaked into, or wedged by what runs in a
session.

Three obligations follow from owning a process for an unbounded period.

The kernel is **killable and interruptible**. Closing the session ends its
kernel; ending a kernel from the list in §4.4 closes its session; a hung cell is
interruptible without ending the session (§6.3).

The kernel is **attributable**. A resident process holding an afternoon's worth
of data is visible in the Explore tab's kernel list with the session it belongs
to and the memory it holds, and can be ended there.

The kernel is **scoped to exploration**. An interactive block asking its
question starts no kernel, and a packaged block's run starts none for a person:
it executes the notebook slice in a subprocess, as a Code Block executes its
script (§6.7).

### 5.4 Installing Into A Live Session

Two known costs are inherited from the bundled runtime and must be handled
rather than discovered later.

Bundled-runtime dependency drift becomes more visible. Reusing
`resources/python` omits dependencies added to `pyproject.toml` after it was
built, and OTA updates cannot ship runtime dependencies. Exploration will make
people encounter missing libraries far more often than workflow execution does,
because exploring is when they reach for something new.

The install path must lead to the right environment. The embedded terminal's
default-to-conda-base defect was fixed for zsh and bash by #1838, and a session
should not depend on that fix holding for every shell. The session offers
installation through the kernel's own `%pip`, which by construction installs
into the environment the kernel is running in.

A session therefore **modifies its own environment**, which workflow runs do
not. An `EnvironmentSnapshot` captured once at session start stops describing
the session as soon as something is installed, so snapshots are taken per
durable execution and stored by reference (§7.4).

### 5.5 Calling A Block From A Cell

A notebook cell may call a SciStudio block:

```python
peaks = blocks.run("imaging.find_peaks", img=img, sigma=2.0)
```

The call **executes inside the kernel**. A thin adapter performs what the
workflow runner performs around a block — port validation, wrapping native
objects into typed `DataObject`s on the way in and unwrapping on the way out,
and translating block exceptions — and returns a native object.

Routing the call through the real runner instead would spawn a subprocess per
call and produce a reference to load back, which is the wrong latency for a
surface whose purpose is rapid iteration. Executing in-kernel forfeits
subprocess isolation, so a block that crashes the interpreter takes the kernel
with it; the kernel is restartable and the notebook replays, and Code Blocks and
App Blocks spawn their own processes regardless, which leaves process blocks as
the only genuinely in-process case.

An interactive block called from a cell opens its panel through §3, rendered by
SciStudio's own surface rather than through the notebook's display protocol. A
cell that calls one therefore only completes inside SciStudio; run elsewhere, it
waits for a panel that will not appear, and a notebook containing such a call
cannot be packaged (§4.6).

Two supporting concerns are noted rather than resolved here. Block versions
recorded in a cell may drift from the installed block, which is the same problem
workflow lineage has and should take the same answer rather than a second one.
And the parameters available for a given block need to be discoverable from
inside the session, which the card panel of §4.4 serves.

## 6. The Notebook

A session with a notebook has one; an interactive block asking its question
does not.

### 6.1 Execution Order And Re-Execution

Classic notebook semantics let a person edit a cell, re-run it, and leave every
downstream cell displaying results computed from the previous value, with
nothing on screen indicating that this has happened. For someone who has not
built the habit of restarting and running everything, the consequence is a
conclusion drawn from a stale number. In a scientific setting this is a
correctness problem rather than an inconvenience.

Reactive notebooks solve it by deriving a dependency graph over cells and
re-running dependents. The well-known implementation of this idea forbids
defining the same variable in two cells, because its graph is keyed on global
variable names and two definitions make a reference ambiguous. That constraint
is unacceptable here: the users this feature targets are Jupyter-fluent, and
`df = df.dropna()` is how they write.

Both properties are available together by keeping **written order** as the
authority. The unit is the **cell**: each cell binds some names and reads some
names, and a cell that reads a name depends on the nearest enabled cell above it
that binds that name.

```python
[1] df = load(...).to_pandas()        # binds df
[2] df = df[df.intensity > 100]       # reads df from cell 1, binds df
[3] peaks = find_peaks(df)            # reads df from cell 2, binds peaks
```

With order fixed, `df` in any cell refers unambiguously to the nearest
definition above it, so the graph is exact at cell granularity and variable
names are reusable. What this model gives up relative to the name-keyed one is
position independence — cells cannot be reordered arbitrarily and have the
system recover their intended order. Notebooks are read top to bottom, so the
loss is theoretical.

Re-execution is **marked, never automatic**. When a cell is re-run, every cell
downstream of it is marked stale, and nothing else happens. A stale mark is a
statement about the screen, and the person decides when to spend the
computation: one control runs the stale set, and a single cell can be run by
hand as always. Re-running dependents automatically is what a reactive notebook
does, and for the analyses these users run it means a filter change triggering
minutes of downstream computation the person did not ask for. Packaging (§4.6)
is where staleness is enforced: a notebook whose declared-output slice contains
a stale cell is not packaged until that cell has been run.

A re-run can also read **out of order**. Cells A, B, and C each bind `df`; the
person runs all three, edits B, and runs B again. Execution semantics are
Jupyter's, so B reads the `df` the namespace holds, which is C's. The graph
says B's `df` comes from A. The session compares the two and marks B out of
order; B runs regardless, and the mark carries a control that runs A and then
B when the person wants A's value. Nothing rebinds a name and nothing holds an
old version of an object: the notebook behaves as Jupyter users expect, and
the mark says where that behaviour disagrees with written order. Packaging
refuses a slice containing an out-of-order cell for the same reason it refuses
a stale one.

Cells can be **enabled and disabled**. A linear notebook has no way to say that
cells 2 and 3 are alternatives rather than steps; disabling one makes the graph
route around it, so a person keeps both candidate filters and switches between
them with a toggle. The graph is built over enabled cells only.

The graph earns three things beyond correctness. It tells the panel layer
exactly which bindings changed, which removes the need to detect mutation in
Python, where `df is not old_df` misses every in-place modification. It bounds
the freeze in §6.3 to the panels a queued execution can affect. And it is what a
packaged block's run selects against (§6.7).

### 6.2 The Dependency Analysis

What a cell **reads** is found statically. The standard library's `symtable`
reports, for each cell, the names it references at module scope, including
reads from nested scopes that resolve to the module scope, and a single `ast`
walk supplies the output and input declarations and the block calls. No
third-party dependency and no IPython is required. Magic and shell lines are
stripped before parsing, a cell that begins with a cell magic is treated as
opaque, and a cell that does not parse is flagged without blocking the others.

What a cell **changes** is observed. When a cell runs, the kernel fingerprints
every top-level name in the namespace before and after, and the names whose
fingerprint changed, appeared, or disappeared are the cell's changed set. That
set is exact within the fingerprint's bound, and it needs no guessing about
in-place mutation, aliasing, deletion, or what a helper does to its argument:
`df.dropna(inplace=True)`, `df2 = df` followed by a mutation of `df2`, and a
call to a function imported from outside the notebook that mutates its
argument are all seen the same way, because the namespace shows what changed.
The first draft of this design recognised in-place mutation from the source
with a list of mutating methods; the list would have been wrong at the margins
forever, and the kernel already has the answer. A change the source did not
show is reported to the person as a diagnostic on the cell.

For a cell that has not run yet, the names it assigns in the source stand in
as the estimate of what it changes. That is the only time an estimate is
needed, because a cell that has never run is neither stale nor packageable. The
graph uses the union of the estimate and the observation, so an observation
can add a definer and never remove one, and a sampled fingerprint that misses
a change in a very large object can at worst leave the graph where the source
put it. Panel-generated code always rebinds and never mutates in place, and
§3.6 enforces that at the queue.

The analysis makes no claim about statement order inside a cell or about
which branch of a conditional runs. Its one guarantee is that the static
estimate never omits an assignment the code shows; it may name one that
execution would not perform. Every consumer tolerates an extra edge — a cell
marked stale unnecessarily, a slice one cell too large, a panel refreshed once
too often — and a missing edge is the stale number this section exists to
remove. Fingerprints are bounded in cost and fall back to identity for types
they cannot inspect, reporting those as unobservable rather than guessing.

### 6.3 The Execution Queue

A value produced by a panel and a hand-run cell can never race, because both are
submitted as executions to a kernel that has one execution queue. Nothing needs
to be locked; the ordering falls out of the queue. The consequence worth stating
is that the notebook's cell-run sequence is a total order over every change to
the session's data, whatever its origin, which is why reproducibility does not
depend on the person's discipline.

Admission to the queue is where the whitelist of §3.6 is applied: code a panel
emits is parsed before it is queued and refused if it contains a statement form
outside the allowed set.

What does need design is what the interface does while an execution is in
flight.

The freeze is **shallow**. A cell may run for minutes, and during that time the
panel continues to zoom, pan, page, and switch views, because it is displaying a
snapshot and reading a stale snapshot harms nothing. What suspends is the
ability to submit a new value. A greyed-out panel would make the session's
primary surface unusable for much of its life.

The freeze is **symmetric**. Code emitted from a panel occupies the queue
exactly as a hand-run cell does, and the notebook waits behind it under the same
indicator.

The freeze has an **exit**. A hung cell must be interruptible, and the interrupt
must actually reach the kernel. This is called out as a requirement because the
product has previously shipped a stop control that did not stop what the person
believed it stopped (#1790).

### 6.4 Two Kinds Of Step

The block calls of §5.5 make the notebook's cells divide into two kinds, and
several later decisions turn on the division.

A block call is **self-describing**: block identifier, version, and resolved
parameters are structured data. A line of pandas is replayable and otherwise
opaque. The distinction propagates into provenance (§7.3), where a block call
records what a workflow node records. It gives someone who cares about the
traceability of a step a concrete reason to reach for a block, without
forbidding them anything.

### 6.5 Storage Format

A session's notebook is stored as **`.ipynb`**. The format is the one these
users already know, it opens in every notebook tool they might carry it to, and
it keeps open the possibility of bringing an existing notebook in. It also
carries an official per-notebook metadata field, which gives the dependency
graph of §6.2 and the session's panel bindings a place to live that other tools
will ignore.

What is committed has its **cell outputs stripped**. Outputs are execution
state, and ARCHITECTURE.md §4.6 already keeps runtime state and large data out
of ordinary commits; in a session they are additionally redundant, because
anything durable is already a reference recorded in §7. The file on disk keeps
its outputs, so someone who opens the notebook in Jupyter or sends it to a
colleague still sees results. Stripping happens on the way into git.

### 6.6 Version History

Each cell run appends a commit containing the notebook at that moment. The
person takes no action, and the history exists because it was never optional.

Measurement decides the shape of the implementation. On the path SciStudio
actually uses — the bundled git binary invoked as `add` then `commit` through
`GitEngine` — a commit of a fifty-cell notebook costs **27–31 ms**, and a
worktree carrying two thousand tracked files does not change that materially
because git's index stat cache absorbs it. Loose objects accumulate at roughly
12 KB per commit and compress by about twenty-five times when packed, so a
thousand cell runs occupy under a megabyte of packed history.

Storage is therefore not a constraint, and the cost that remains is latency in
the wrong place. Thirty milliseconds is invisible against a cell that takes half
a second and is fifteen times the cost of a cell that filters a small frame. The
commit therefore happens **off the execution path**: the result returns to the
interface, and the commit is queued behind it. The queued commit records the
notebook as captured at execution time rather than as read from disk, so a
second cell run during the interval cannot corrupt the first commit's content.

Volume is a genuine constraint, and it lands on history rather than on disk. A
thousand commits a day accumulate on a branch that, under §4.5, represents one
data context and carries that context's workflow history. Burying that history
under machine-generated commits would take away the reason branches are useful
here.

Explore commits are therefore written to a **dedicated ref namespace** rather
than to the branch. The fine-grained history stays addressable, lineage records
reference its shas, and `git log` on the branch continues to describe what a
person did. A session writes a single meaningful commit onto the branch when the
person asks for one or when the session ends.

Because the project ships its own git, packing must be ensured rather than
assumed; git's default auto-gc threshold of 6700 loose objects corresponds to
roughly a week of heavy use.

### 6.7 Running A Packaged Block

A packaged block (§4.6) runs with no interface, no panels, and no kernel held
for a person. What runs is the **backward slice of the declared outputs** —
every enabled cell the `scistudio.output(...)` call transitively depends on, and
nothing else. A session accumulates abandoned experiments, scratch prints, and
cells that failed and were left in place; none of that belongs in a workflow
run, and the dependency graph of §6.2 makes the selection exact rather than
heuristic. The rule is explainable in one sentence, and the interface says which
cells a packaged block will execute.

The execution path is the one Code Blocks already have for notebooks: the
notebook backend runs an `.ipynb` in a subprocess with the bundled interpreter
(§5.1), and packaging adds the slice filter and the port bindings. A notebook
that calls an interactive block cannot be packaged (§4.6); this is detected at
packaging rather than at run time.

Reopening a packaged block's notebook (§4.4) changes nothing about how the block
runs until the person packages again.

## 7. Lineage

### 7.1 The Session Anchor

Lineage today is four tables: `runs`, `block_executions`, `data_objects`, and
`block_io`, with object identity carried in a `DataObject`'s framework metadata
(`core/lineage/record.py`). A session needs the same downstream structure and a
different anchor, because what happened in it was not a workflow run and the
session is not a node.

One table is added. `explore_sessions` parallels `runs` field for field: where a
`RunRecord` carries `workflow_id`, `workflow_yaml_snapshot`, and
`workflow_git_commit`, a session carries the notebook's path, its captured
content, and the commit written in §6.6. Both carry an environment snapshot, a
start time, and a status.

A packaged block's run is an ordinary run. Its `BlockExecutionRecord` records
the block as any block is recorded, and the block's version is the notebook
commit it was packaged from, so the exploration that produced a step is
reachable from the step. An interactive block asking its question needs none of
this: its decision is already recorded as an `interactive_response` in the run's
lineage, exactly as ADR-051 specifies.

### 7.2 What Is Shared With Workflow Lineage

The other three tables are used unchanged. A block call from a cell writes an
ordinary `BlockExecutionRecord` — `block_id`, `block_type`, `block_version`,
`block_config_resolved` are the fields it already has — with its foreign key
pointing at a session instead of a run. Objects and their input/output edges go
into `data_objects` and `block_io` as they always have.

Independence therefore stops at the anchor, and the chain across the boundary
stays intact through `object_id`. A reference produced while exploring and later
consumed by a workflow appears as that run's input, and the session side records
where it came from. Following provenance across the boundary requires no
bridging code, because content identity is already the shared key.

### 7.3 Graded Provenance

The grade follows the division in §6.4. A block-call cell records what a
workflow node records. A free-form cell records the session, the notebook
commit, the cell, and the environment — enough to replay, and not enough to
describe. Replaying is well defined because the notebook loads its own inputs in
cell one and executes in written order.

### 7.4 Recording Rate And Cost

Records are written per cell run, which costs **0.07 ms and 212 bytes** on the
existing SQLite store in WAL mode. At a thousand cell runs a day this is 70 ms
and 212 KB, so the recording rate needs no rationing.

The environment snapshot is the one field that must not be inlined per record:
`EnvironmentSnapshot` carries an optional full `pip freeze`, and duplicating it
into every cell run would turn a 212-byte row into a five-figure one. It is
stored once per distinct environment and referenced, which also accommodates the
mid-session installs of §5.4.

### 7.5 Retention

Retention reuses a decision the session already makes. Exploration produces many
intermediate objects and abandons most of them; the objects named in
`scistudio.output(...)` are durable, and the remainder are reclaim candidates
for the existing planner in `core/lineage/retention.py`. No new user-facing
concept is introduced to express this.

## 8. AI Integration

The agent is the intended author of most of what this ADR introduces. ADR-053 §4
records the reasoning for blocks, §3.2 above records it again for panels, and
the same holds for notebooks: someone who does not want to write pandas will ask
the agent to write the cells. A design whose authoring path runs through an
agent that has never heard of it is not delivered until the agent has been
taught.

### 8.1 What The Agent Has To Learn

The agent is currently taught two authoring surfaces. `scistudio-write-block`
covers authoring a block file and names the optional interactive, App, and Code
shapes neutrally; `scistudio-write-plot`, added by ADR-048 SPEC 2, covers a
preview-only plot job. Neither describes anything in this ADR, and one of them
now describes the wrong thing.

Three new facts have to reach it.

**A panel is a document, not a module.** Today the agent writes an ES module
against one of two host APIs depending on whether it is building a previewer or
an interactive block's window. After §3 it writes a self-contained HTML file,
declares one of two capabilities, and talks over one message contract. The
existing instructions describe a form that will no longer be current, so leaving
them in place is worse than having none.

**A notebook can become a block, and choosing that path is a judgement.** When
the agent is asked for a step whose computation is not yet understood, the
right move is to open a session over the data, work it out in cells, and package
the result (§4.6), rather than to guess at a Python block. It is exactly the
kind of decision an agent should be able to make and explain rather than default
into, and it joins the shapes `scistudio-write-block` already presents.

**A notebook that will become a block's implementation has conventions.** Read
inputs through the port (§4.3), declare outputs in code (§4.3), rebind rather
than mutate in place so the dependency analysis sees the edge (§6.2), and reach
for a block call where a block already does the job (§6.4). An agent writing
cells without these produces a notebook that works while someone watches and
misbehaves once packaged.

### 8.2 Where The Teaching Goes

SciStudio already layers its agent-facing material, and this ADR adds to that
layering rather than growing a parallel one. A skill carries the task flow and
stays short, with no inline code. The contract documents under
`.scistudio/agent-reference/` carry the shapes and rules. The generated
`user-guide/api-reference/` carries exact signatures. Worked patterns are
fetched through `list_block_examples` rather than pasted into a skill.

Each new fact therefore lands in one place. `panel-contract.md` joins the
agent-reference set and is the single description of the capability
declaration, the message contract, the on-disk layout of §3.3, and the tier a
panel should be written into. `block-contract.md` gains the packaged-notebook shape beside
the shapes it already names. The examples corpus gains a panel and a session, so
the agent reads a real one instead of reconstructing it from prose.

### 8.3 The Skill Bundle

ADR-040 §3.4 defines the bundle — one base index and a set of task-scoped
skills, installed into both `<project>/.claude/skills/` and
`<project>/.agents/skills/` — and ADR-048 SPEC 2 established that a new
authoring surface earns a skill. This ADR follows that precedent once.

**`scistudio-write-panel` is added.** Authoring a panel is a distinct task with
its own flow: decide the capability, choose the tier, write the document, check
it renders, register it. Folding it into `scistudio-write-block` would bury it
under a skill whose description is about Python files.

**`scistudio-write-block` changes** to present the packaged-notebook shape and to route to
the panel skill when what the user actually wants is a window.

**Authoring cells inside an open session is not a new skill.** The agent doing
that is already inside a session someone opened, working against tools rather
than choosing a task shape, so the conventions of §8.1 belong in a reference
document the session's tools point at. This keeps the bundle from growing a
skill whose description would overlap the one the user just acted on, at the
cost of the conventions being slightly less prominent; if that proves too quiet
in practice, it becomes a skill.

### 8.4 The Tools The Work Needs

The authoring tools that exist for blocks — `read_block_source`,
`list_block_examples`, `scaffold_block`, `reload_blocks`, `run_block_tests` —
describe the shape the panel and session equivalents should take, and the
equivalents are missing.

An agent authoring a panel needs to scaffold one into a chosen tier, read an
existing one, and make the registry pick up what it wrote. An agent working
inside a session needs to read the notebook and its dependency graph, append and
run cells, see the current bindings, and execute the declared-output slice
as a packaged block would, to confirm the notebook will behave once packaged. The last of
these matters most: it is the only way an agent can tell the difference between
a session that works because a person is watching and one that will run.

Adding these carries a contract cost that is easy to miss and easy to state.
Every change to the agent's MCP tool set moves a set of count assertions in the
test suite and a set of live catalog documents; a tool added without updating
them fails the suite in places that do not mention the tool. The work plans for
that rather than discovering it.

### 8.5 The Agent Has To Be Able To See Its Panel Work

§3.2 chose the panel's authoring form partly on the grounds that an agent can
open a plain HTML file in a browser with stub data and look at the result. That
argument is only sound if the harness actually delivers the loop, and it does
not deliver itself.

A scaffolded panel therefore ships with the stub harness that makes it openable
on its own: representative data for the types it declares, and a stand-in for
the host side of the message contract so the panel's outbound path can be
exercised without a session. The agent's existing browser-driven debugging path
is the mechanism; what is new is that a panel is born ready for it.

Without this, §3.2's central justification degrades into an assertion, and the
format chosen for agent authorability would be no easier to author than the one
it replaced.

## 9. The Shape Of The Implementation

A unification that exists in this document and not in the tree is not a
unification. The failure mode is concrete and common: the panel contract is
agreed, a third module is added beside the two that already exist, each keeps
its own manifest type and its own loader, and within two releases there are
three implementations of one idea plus a document claiming otherwise. This
section states the code shape the design requires, because leaving it to
implementation is how the outcome above happens.

The rule is that **the panel is one implementation whose differences are
parameters**. Where two uses genuinely differ, the difference is an argument, a
declared capability, or a strategy — never a second copy of the mechanism.

### 9.1 What Is One Thing, And What Differs

One thing, with exactly one implementation each: the panel document format and
its manifest, the validate-load-mount sequence, the API version gate, asset
serving and its path confinement, the host-to-panel message contract, the
behaviour when a panel fails to load, and the four-tier discovery machinery.

Legitimately different, expressed as parameters of the above: **how a panel is
addressed** — by the type of the data (the routing ladder) or by name from the
block that opens it (§3.3) — and **which outbound path the host grants**, which
is the capability declaration of §3.1. A third difference, what is done
with a produced value, belongs to where the panel is mounted (§3.1) and never
reaches the panel code at all.

Two implementations of the load sequence differing only in their asset route is
the situation this ADR exists to end, so the migration in §10.1 is complete when
`dynamicPreviewer.ts` and `panelModuleLoader.ts` are one module and
`PANEL_API_VERSION` and the previewer's API version are one constant.

### 9.2 Where The Shared Contract Lives

The panel manifest, the capability declaration, and the version gate are
imported by parts of the tree that cannot import each other.
`blocks/base/interactive.py` declares a manifest and sits in the block layer;
the panel subsystem serves and validates manifests and sits above it; the API
layer routes them. A contract with consumers spanning layers cannot live in any
one of those layers.

SciStudio has already answered this exact question once. `core/origins.py`
records that it sits in `scistudio.core` because "its consumers span layers, and
no layer above `core` may be imported by the others", which is why the tier
roots live in `core/dropins.py` and not inside the block or type registries. The
panel contract takes the same placement for the same reason, leaving the
subsystem to own the registry, the routing ladder, the asset route, and the
session-side host.

Getting this wrong has a specific shape worth naming: a shared type left inside
the panel subsystem forces the block layer to import upward, and the pressure to
relieve that produces a second manifest type in the block layer — the exact
duplication this section exists to prevent, arrived at through a layering
constraint rather than through carelessness.

The layer test enumerates the subsystems it checks, so introducing or renaming
one moves that enumeration. This is the same class of obligation as the MCP tool
counts in §8.4: cheap when planned, confusing when discovered.

### 9.3 One Vocabulary

The concept is the panel; `previewer` names one of its two capabilities. Code
that keeps `previewer`, `interactive panel`, and `explore panel` as three nouns
will keep three of everything else, because a reader with three names has no
signal that they are looking at one thing.

The rename is mechanical and the behaviour change is not, so they should be
separate commits rather than separate releases. Splitting them across releases
leaves the tree stating one thing and the document another for the duration,
which is the confusion this section is written to avoid; combining them into one
commit produces a diff no reviewer can read.

### 9.4 Compatibility Has An End

§10.1 retains compatibility while packages migrate, and a compatibility shim
with no removal condition is a second implementation with a friendly name. The
shim exists to let `scistudio-blocks-imaging` and any project-local previewer
cross the contract change, and it is removed in the same track once they have,
with the removal named in the ADR-048 addendum rather than left to a later
judgement call.

The one thing the shim must not do is grow a feature. A package that has not
migrated keeps working; it does not get the session bindings or the producing
capability without moving to the contract, because a shim that accretes the new
surface becomes the second implementation permanently.

## 10. Delivery

### 10.1 Migration Order

The panel contract of §3 lands first, with the existing loaders migrated onto it
and compatibility retained. The dependency analysis of §6.2 lands beside it,
since it depends on nothing and three later pieces depend on it. The session
service, the kernel, and packaging follow; the Explore tab is built on the
session API once that API exists, and the interactive-block modal is retired in
the same step; the agent harness of §8 lands last.

The order is chosen so that the contract meets real panels before it acquires
dependents. Between them, previewers and interactive-block panels already
exercise both discovery mechanisms, both capabilities, the loading path, the
version gate, and the failure behaviour, none of which are specific to
exploration. A contract that has already carried the imaging previewer and an
interactive block's window is one the new work can build on; a contract designed
against exploration alone would meet those cases afterward, when changing it is
expensive.

Moving previewers from the ADR-048 ES-module contract to the unified one is a
breaking change to a contract that packages already implement, and it requires
an addendum to ADR-048, a corresponding addendum to ADR-051 for the panel side,
and a migration for `scistudio-blocks-imaging`. Doing it now is materially
cheaper than doing it after more packages ship panel assets. The asset whitelist
in `previewers/assets.py` gains the file types the unified contract serves, and
the two API versions become one.

### 10.2 Scope

In scope: the unified panel contract, its migration, and the editing of panels;
the Explore Session as a notebook and kernel over data; the Explore tab as the
one interaction surface, replacing the modal; the notebook's execution
semantics, dependency analysis, storage, and per-cell-run commits on a dedicated
ref; in-kernel block calls; packaging a notebook into a block and running its
declared-output slice; the one remember setting of §4.7; the `explore_sessions`
lineage anchor; and the agent harness of §8 — the added skill, the panel
contract reference, the panel and session tools, and the stub harness a
scaffolded panel ships with. The code shape of §9 is a constraint on all of it
rather than a separate deliverable.

Out of scope: replacing the workflow editing mode; a general-purpose notebook
IDE; modification of existing artifacts in place; automatic merging of branches;
importing external `.ipynb` files, which §6.2's analysis would need to report on
rather than assume; lifting block calls out of a notebook onto the canvas as
nodes of their own (§4.6); and the producing capability for the plot panel
(#2212).

### 10.3 Staging

A first slice covers one data type, a small set of producing panels, the session
service and its kernel, panel-to-code generation, packaging, and enough of §8
that the agent can author a panel for that data type. That is enough to test
whether the loop is worth using before array and image panels, the graph view,
and the retirement of the interactive-block modal are built.

## 11. Verification And Tooling Impact

This ADR is in planning phase and governs no implementation yet; the surfaces in
`planned_governs` become governed as they land.

Verification expectations by area. The dependency analysis needs unit coverage
over the assignment forms it must recognise, the observation per type, and a
differential test that executes fixture notebooks and confirms that running
only the backward slice of the declared outputs reproduces the whole
notebook's outputs. The unified panel contract
needs the loader tests the two existing loaders already carry, run against one
implementation, plus coverage that a displaying panel is given no outbound
path, that emitted code outside the whitelist of §3.6 is refused, and that
editing a built-in panel copies, reloads, and reverts. Kernel lifecycle needs
coverage of restart, interrupt during a hung cell, ending a kernel from the
list, retirement on branch switch, and environment re-snapshot after an install.
Packaging needs coverage that a notebook with a stale cell in its slice or a
call to an interactive block is refused, that ports come from the declarations,
and that the packaged block runs exactly the slice. The remember setting needs
coverage that a packaged block replays across changed inputs while an authored
interactive block still asks. Lineage needs coverage that an object produced in
a session and consumed by a workflow run resolves across the boundary, and that
a packaged block's run records the notebook commit. The Explore tab needs
coverage that an interactive block's pause opens it with no notebook pane and
that confirm and cancel reach the engine as the modal's did. The agent harness
needs the provisioning coverage the skill bundle already carries, extended to
the added skill, and the count assertions and catalog documents that every MCP
tool change moves (§8.4). The code shape of §9 is verified by the architecture
layer test, which must show the panel contract in `core` and no upward import
from the block layer, and by the absence of a second load sequence once the
migration is done.

The commit and lineage measurements in §6.6 and §7.4 were taken on the paths
this ADR relies on and should be re-taken if `GitEngine`'s invocation pattern or
the lineage store's durability settings change.

## 12. Consequences And Risks

Exploration will surface missing dependencies far more often than workflow
execution does, and the bundled runtime cannot receive them through OTA. The
`%pip` path in §5.4 is the mitigation, and its adequacy is the single most
likely early blocker on this feature being usable.

A session holds a process for as long as someone keeps it open. §5.3 confines
the cost and keeps the engine clean, and the obligations it lists — killable,
attributable, scoped to exploration — are what stop a long-lived kernel from
becoming an untracked resource leak.

In-kernel block execution means a block that crashes the interpreter ends the
session. Recovery is a restart and a replay, which is acceptable, and which
depends on the replay property holding — so anything that weakens the
port-based first cell weakens crash recovery too.

What a cell changes is known only after it has run. Until then the source's
assignments are the estimate, and an in-place mutation the source does not
show is invisible; the window has no consequence, because a cell that has
never run is neither stale nor packageable, and packaging refuses a slice
containing one.

Retiring the modal changes how every existing interactive block is presented.
Their compute path is untouched, so the risk is confined to the frontend
surface, which the Explore tab's tests cover.

A packaged block and the exploration it came from can diverge. This is
accepted: the block owns its notebook and is the product, and the session is
the history.

Migrating previewers breaks a shipped contract. The cost is a package migration
now against a larger one later.

## 13. Alternatives Considered

### 13.1 A Session That Is A Block From Creation

The second shape of this design — the one this ADR recorded before its revision
— made an Explore Session a workflow node from the moment it was created, so
that no packaging step existed. It was abandoned because it described
exploration in the vocabulary of ADR-051's pause: a session became a block that
pauses, takes a decision, is remembered, and runs headlessly, and every later
section inherited that framing. The common case — looking at the output of a
block that has already run, with no run in progress — read as the exception,
exploration without a workflow was impossible, and the engine was involved in
something that is not a workflow step.

The first shape, a standalone notebook converted into a workflow subgraph,
remains rejected for the reasons that killed it: how finely to split a sequence
of statements into nodes, which of a person's branches were intentional rather
than incidental, how to render a generated graph on a canvas that had no
positions for it, and how to keep the promoted copy from drifting away from the
notebook it came from. Packaging (§4.6) raises none of them, because it makes
one block and infers nothing: the block's ports are declared in code, its
position is where the person drops it, and it owns its notebook.

### 13.2 AnyWidget Modules Instead Of Framed HTML Documents

Authoring panels as AnyWidget modules — an ES module exporting
`render({ model, el })` against a Python object whose traits synchronise with
the front end — would let a notebook's panels render in JupyterLab, VS Code, and
Colab, matching the portability motive behind storing notebooks as `.ipynb`.

It was rejected on two grounds. The portability it buys is narrower than it
appears: a notebook taken elsewhere already executes all of its code and
describes its own inputs, so what travelling panels would add is SciStudio's own
interactive surface inside someone else's tool.

The second ground is decisive given who writes these panels. Against a
self-contained HTML document, an AnyWidget module is harder for an agent to
author well: it cannot be rendered and inspected without a running kernel, its
trait and event vocabulary is represented in far less public material than plain
HTML, and a mistake in it executes in the application's own realm rather than in
a frame that can be discarded. Trait synchronisation would also have given a
panel a way to change data without leaving code behind, which the frame boundary
makes structurally impossible.

### 13.3 Name-Keyed Reactive Semantics

Deriving the dependency graph from global variable names is the established
approach and removes the ordering requirement in §6.1. It forbids defining a
variable twice, which the target users do constantly. Adopting it would have
required teaching Jupyter-fluent scientists to write differently in exchange for
a property they can get without changing anything.

### 13.4 Executing Blocks Through The Workflow Runner

Submitting a notebook block call to the real engine would produce artifacts and
lineage identical to a workflow run and would isolate the block in a subprocess.
It was rejected on latency: a subprocess launch and an artifact round trip per
call is the wrong cost for a surface built for iteration. The provenance
difference is smaller than it appears, because §7.2 records the same
`BlockExecutionRecord` either way.

### 13.5 Storing Notebooks As Text

A percent-format `.py` produces readable diffs and straightforward text merges,
and the JSON structure of `.ipynb` produces neither. The reasons for `.ipynb`
are given in §6.5; what remains is whether the diff argument should have
outweighed them, and it should not. Propagating an improvement between data
contexts operates on the dependency graph of §6.2 — a connected subgraph, its
inputs rebound — so the mechanism that would have depended on legible text does
not use text at all. Stripping outputs removes most of the remaining noise.

### 13.6 One Session Per Branch

Restricting a branch to a single session would simplify lifecycle. It conflicts
with how the branching model is used: a branch is one data context, and a person
may reasonably explore that context from several angles at once.

### 13.7 Running The Whole Notebook Headlessly

Executing every cell rather than the declared-output slice would keep the file
on disk and the run identical. It was rejected because a session's cells include
abandoned experiments and cells that failed and were left in place, which would
make production runs slower and less reliable than the analysis they encode. The
dependency graph makes the slice exact, so the alternative buys nothing beyond
the appearance of literalness.
